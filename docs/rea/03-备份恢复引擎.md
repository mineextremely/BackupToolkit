# 03 · 备份 / 恢复引擎

> 引擎主体 = `res/raw/root_shrc.sh`（335 行，全文注释见 `附录A-root_shrc-注释.md`）。
> Java 侧只负责「选谁、选哪些档位、起什么命令、写什么 JSON」。

---

## 1. 分层视图

```
UI（AppBackupRestoreActivity / AppInfoActivity）
   │ 用户勾选 3 个档位（apk / user / data）× N 个应用
   ▼
编排器 c.Cimport（Runnable，单线程执行）
   │ ① app_init <uid> <backupHome> <isBackup> <compatMode>
   │ ② (备份时) compress_init <扩展名> <压缩等级>
   │ ③ 逐应用：app_backup|app_restore <pkg> <backupTime> 'apk&&user&&data'
   │ ④ 用 FileSystemService 写 !BackupInfo!<pkg>.json / !icon!<pkg>
   ▼
root shell（长生命周期，已 source root_shrc.sh）
   │ killall / tar / zstd / busybox / pm / am / chown / restorecon
   ▼
备份目录（SD 卡 / OTG / rclone 云盘挂载点）
```

数据结构上的「档位」只有 3 个（`c.Creturn.f633new = {"apk","user","data"}`），每个档位在 shell 里展开成多个 tar 分卷：

| 档位 | 备份内容 | 产物分卷 |
|---|---|---|
| `apk` | `pm path` 列出的 base.apk + 所有 split apk；`/sdcard/Android/obb/<pkg>` | `<ts>-apk<ext>`、`<ts>-apk_obb<ext>` |
| `user` | `/data/user/<uid>/<pkg>`（排除 `lib/oat/cache/code_cache/no_backup`）+ `/data/user_de/<uid>/<pkg>`（同排除） | `<ts>-user<ext>`、`<ts>-user_de<ext>` |
| `data` | `/sdcard/Android/data/<pkg>`（排除 `cache`） | `<ts>-data<ext>` |

> 注意命名反直觉：`user` 是**内部数据**（`/data/user*`），`data` 是**共享存储里的 Android/data**。UI 文案也照此解释（`backup_restore_description`）。

## 2. Java 侧编排细节（`c.Cimport`）

```java
// 备份：pkg, backupTime(ms), modes, 日志回调
String.format("app_backup %s %s '%s'", pkg, backupTime, modes)
// 恢复：同上
String.format("app_restore %s %s '%s'", pkg, backupTime, modes)
// 初始化（每次任务一次）：
String.format("app_init %s %s %s %s", uid, backupHome, isBackup?1:0, compat?1:0)
String.format("test $? -eq 0 && compress_init %s %s", ext, level)
```

> REA 证据（2026-10-19）：`c.Cimport.m435extends` = `ev_316f6ad8…`（`app_backup`）、`m437package` = `ev_17919a1a…`（`app_restore`）、`m436finally` = `ev_08d42e0d…`（`app_init` + `compress_init`）。`app_sort` 只在 DEX 字符串中出现，调用点尚未确认。

要点：

1. **`backupTime` 同时是分卷文件名前缀（CPId）**：`System.currentTimeMillis()`，一次批量任务里对每个应用单独取当前时间。
2. 恢复前会先扫描该应用目录，把存在的分卷登记进 `Boolean[]`（`null` 表示「这一档存在」），UI 据此把不存在的档位置灰。
3. 每个应用跑完后立即落盘 `!BackupInfo!<pkg>.json`（增量写、可中断），失败则记入日志并在结尾汇总「失败的数量 / 失败的包名」。
4. 「备份自身」：当 `backup_self=true` 且备份目录 `config.json` 记录的版本与当前 App 版本不一致时，追加
   `rm -f '<home>'/*.apk*; cp '<自身 APK>' '<home>/!app!.apk'`
   并把 `{"versionName":"1.1.1","versionCode":1113}` 写入 `config.json`（用 FileSystemService 写）。
5. `finish_consolidation`（`完成时显示提示`）与 `top_version_diff` 等属于纯 UI 偏好。

## 3. shell 引擎逐段语义

### 3.1 环境与依赖

```sh
export TMPDIR=/data/local/tmp
alias zstd='zstd -T0 -qr --ultra --priority=rt'
add_busybox_applet unzip tar realpath find awk grep killall
alias STI='toolkit st_info'        # 取 size / uid
alias LZ='/system/bin/ls -Z'       # 取 SELinux 上下文
```

- `-T0` 用满所有核心；`--ultra` 放开 19 级以上；`--priority=rt` 抢实时优先级（备份时降低卡顿感知，代价是可能影响前台）。
- 精简版 busybox **故意只保留 7 个 applet**（tar/unzip/realpath/find/awk/grep/killall），因此没有 `stat` → 用自研 `toolkit st_info` 补齐。
- `toolkit` 是自研 ELF，唯一子命令 `st_info`：`toolkit st_info <path> s|u|g` 分别输出 `stat.st_size`（`%ld`/`%lld`）、`st_uid`（`%u`）、`st_gid`（`%u`）；只导入 `stat`/`printf`，无 exec/网络/写文件。脚本实际只用 `s`（APK 字节数）与 `u`（uid），`g` 分支未被使用。来源：`readelf`/`objdump` + 四 ABI 对照（非 REA 台账）。

### 3.2 APK 安装命令适配

```sh
SDK_INT >= 34 : pm_install='pm install -r -t -d -i com.android.vending --bypass-low-target-sdk-block'
               pm_create ='pm install-create -r -t -d -i com.android.vending --bypass-low-target-sdk-block'
否则          : 去掉 --bypass-low-target-sdk-block
```

- `-r` 覆盖安装、`-t` 允许 test-only、`-d` 允许降级、`-i com.android.vending` **伪装成 Play 商店安装来源**（绕过部分 ROM 的「未知来源」/安装来源校验）。
- Android 14 起低 targetSdk 应用会被拒装，故加 `--bypass-low-target-sdk-block`。

### 3.3 `app_init(userId, backupHome, isBackup, compatMode)`

职责：确定存储根 + 定义本次任务要用的「动作函数」。

```sh
sd_android=/data/media/<userId>/Android
[ userId -eq 0 ] && [ ! -d "$sd_android" ] && sd_android=$(realpath /sdcard)/Android
[ ! -d "$sd_android" ] && echo '!!未找到用户存储:'<uid> && return 1
```

- 多用户时用 `/data/media/<uid>/Android` 直取（root 下可读），0 号用户用 `/sdcard` 的真实路径。
- `pm_path()`：主用户 `pm path <pkg>`；其他用户 `pm path --user <uid> <pkg>`。
- 备份模式定义：

```sh
apk(){ backup_apk && backup apk_obb; }
data(){ backup data cache; }
user(){ backup user lib oat cache code_cache no_backup && backup user_de lib oat cache code_cache no_backup; }
```

- 恢复模式定义：

```sh
apk(){ restore_apk && restore apk_obb; }
data(){ restore data; }
user(){ restore_user && restore user_de 1; }      # 1 = 额外恢复 SELinux 上下文
```

- 兼容模式（`$4=1`）时安装函数换成 stdin 管道版：

```sh
install_apk(){ cat "$1" | pm_install --user $USER_ID -S $(STI "$1" s) 2>&1; }   # SDK>=23
install_apks(){ cat "$2" | pm install-write -S $(STI "$2" s) "$1" "${2##*/}" -; }
```

> 兼容模式存在的原因（更新日志）：「支持光速虚拟机安卓10」「不能恢复apk才需开启」——某些 VM/魔改 ROM 下 `pm install <path>` 读不到 App 侧私有路径，必须走 stdin。

### 3.4 `compress_init(ext, level)` / `compress` / `decompress`

```sh
parse_ext(): .tar→tar, .tar.gz→gzip, .tar.xz→xz, .tar.zst→zstd, .tar.lz4→lz4
level: 缺省 3，夹到 [1,19]
compress_to_file = "-f"                                # 纯 tar
                 | "| zstd -<level> --format=<fmt> -fo" # 其它
[ -f "$_BACKUP_HOME/.nomedia" ] || { mkdir -p "$_BACKUP_HOME"; touch .../.nomedia; }
```

**一个 zstd 二进制同时产出 4 种压缩格式**（`--format=gzip|xz|lz4|zstd`），免去打包 4 个工具 —— 这是很值得保留的设计。

```sh
compress <path|tar-options> <out> [excludes...]
  绝对路径时: tar -c -C '<父目录>' '<名字>' --exclude='<名字>/<x>' ... $compress_to_file '<out>'
  否则      : tar -c <tar_options> $compress_to_file '<out>'
decompress <file> <dir> [tar-opts]
  tar  --format 时: tar -xC <dir> -f <file>
  压缩格式时     : zstd --format=<fmt> -dc <file> | tar -xC <dir>
```

### 3.5 `backup_apk()` —— 分包应用处理

```sh
for val in $(pm_path); do
  val=${val#*:}                                   # 去掉 "package:" 前缀
  [[ "$val" != /data/* && -z $(unzip -lqq "$val" classes.dex) ]] && echo "跳过" && return
  dir=${val%/*}
  if [ "$_C" != "$dir" ]; then _C=$dir; tar_opts="$tar_opts -C '$dir' '${val##*/}'"
  else tar_opts="$tar_opts '${val##*/}'"; fi
done
```

- 关键过滤：**不在 `/data/` 下且压缩包里没有 `classes.dex`** 的视为系统框架 APK，跳过（避免备份 `/system/framework/*.apk`）。
- 同一目录的多个 split 只用一个 `-C`，tar 参数最小化。

### 3.6 `backup <name> [excludes...]`

```sh
path=$(eval echo \$app_<name>_path)
[ -d "$path" ] || { echo '跳过'; return; }
rm -f "$CP_prefix<name>.tar"*
compress "$path" "$CP_prefix<name>$_BACKUP_EXT" "$@"
```

先删同名旧分卷（避免 `覆盖备份` 时残留 `-apk.tar.zst` 与 `-apk.tar.gz` 共存）。

### 3.7 `restore <name> [recon]` —— 带回滚的原子恢复

```sh
mv "$path" "${path}_old" 2>/dev/null
if decompress "$CP" "${path%/*}" -o; then      # tar -o：解包时不做属主还原
    rm -rf "${path}_old"
    chown -hR "$app_uid:$app_uid" "$path"       # 关键：属主还原成目标应用 uid
    [ -n "$2" ] && recon "$path"                # 可选：SELinux 上下文还原
else
    rm -rf "$path"; mv "${path}_old" "$path"    # 失败整体回滚
fi
```

`recon()`：

```sh
restorecon -F "$1"                                    # 先让系统按策略打默认标签
ctx=$(LZ -d "$1" | awk '{print $1}')                  # 取父目录当前上下文
[ -n "$ctx" ] && /system/bin/chcon -R "${ctx%:c*}" "$1"  # 再把 :c<类别> 后缀剥掉统一刷
```

> 目的：`/data/user/0/<pkg>` 属于 app_data_file 域，若标签错乱，应用会因 SELinux 拒绝而闪退。这是「恢复后应用能正常打开」的关键一步。

### 3.8 `restore_user()` —— 额外处理 `lib` 软链

```sh
local app_lib=$app_user_path/lib
[ -h "$app_lib" ] && local app_libD=$(realpath "$app_lib")   # 先记住 lib → /data/app/.../lib/arm64 的指向
mv "$app_user_path" "$old"; decompress ... || 回滚
[ -n "$app_libD" ] && ln -s "$app_libD" "$app_lib"           # 解包后重建软链
chown -hR "$app_uid:$app_uid" "$app_user_path"
recon "$app_user_path"                                        # 内部数据**总是**恢复上下文
```

`lib` 被排除在 tar 外（是软链且指向当前安装目录），恢复时必须重建，否则应用加载 native so 失败 —— 更新日志「修复恢复数据之后无执行权限的问题(Termux)」应与此相关。

### 3.9 `restore_apk()` —— 单包 / 分包两条路径

```sh
not_file "$apk_CP" '跳过' && return
rm -f "$TMPDIR/"*.apk
decompress "$apk_CP" "$TMPDIR"
apks=$(find "$TMPDIR" -maxdepth 1 -name '*.apk' -type f)
case $(echo "$apks" | grep -c .) in
  0)  echo '没有apk！'
  1)  install_apk "$apks"
  *)  session=$(pm_create --user $_USER_ID | grep -o '[0-9]*')
      for apk in $apks; do install_apks $session "$apk" || { pm install-abandon $session; break; }; done
      pm install-commit $session
esac
```

- 解包到 `/data/local/tmp`（root 可读写、App 也能读的公共临时区）；
- 单 APK 走 `pm install`，多 APK（Split）走 `install-create/write/commit` 会话；
- 失败时 `pm install-abandon` 清理会话，不留半装状态。

### 3.10 `app_backup` / `app_restore` —— 任务外壳

```sh
app_backup(pkg, cpId, mode):
  app_path_init pkg cpId
  mkdir -p "$save_path"
  killall -s STOP "$pkg"        # 冻结，避免数据在打包过程中变动
  eval "$mode"
  S=$?
  killall -s CONT "$pkg"        # 解冻
  [ $S -ne 0 ] && echo '备份错误' && return 1

app_restore(pkg, cpId, mode):
  app_path_init pkg cpId
  for f in "$CP_prefix"*'.tar'*; do n=${f##*<cpId>-}; n=${n%.tar*}; eval "${n}_CP='$f'"; done
  stop_app(){ am force-stop --user $USER_ID $pkg; stop_app(){ return; }; }   # 只停一次
  eval "$mode"
  unset app_uid apk_CP apk_obb_CP user_CP user_de_CP data_CP
  rm -f "$TMPDIR/"*.apk
```

`get_app_uid()` 的三级回退（很重要，恢复必须知道目标 uid）：

```sh
app_uid=$(STI "$app_user_path" u)                          # 1. 现有目录属主
   || app_uid=$USER_ID$(cat /config/sdcardfs/$pkg/appid)   # 2. sdcardfs 映射
   || app_uid=$USER_ID$(grep -o "^$pkg [0-9]*" /data/system/packages.list | ...)  # 3. packages.list
```

## 4. 目录与文件布局

```
<backup_home>/                          # 默认 <sdcard>/Backups/BackupToolkit
├── .nomedia                            # 防止相册扫描
├── config.json                         # {"versionName":"1.1.1","versionCode":1113}
├── !app!.apk                           # 「备份自身」的安装包
└── AppBackup/
    └── <pkg>/
        ├── !BackupInfo!<pkg>.json      # 备份列表元数据（见 04）

        ├── 1730000000000-user.tar.zst
        ├── 1730000000000-user_de.tar.zst
```

- 分卷名正则：`([0-9]+-)[a-z]+(?:_[a-z]+|)\.tar(?:\.[a-z]+|)`

## 5. 完整一次「备份 1 个应用」的命令序列（还原示例）

```sh
# 任务开始（每个批次一次）
app_init 0 /storage/emulated/0/Backups/BackupToolkit 1 0
test $? -eq 0 && compress_init .tar.zst 3

# 每个被选中应用
app_backup com.example.app 1730000000000 'apk&&user&&data'

# 展开后实际执行（伪代码）
mkdir -p /storage/emulated/0/Backups/BackupToolkit/AppBackup/com.example.app
killall -s STOP com.example.app
  tar -c -C /data/app/~~xx==/com.example.app-1 'base.apk' 'split_config.arm64_v8a.apk' \
      | zstd -3 --format=zstd -fo '…/1730000000000-apk.tar.zst'
  tar -c -C /storage/emulated/0/Android/obb 'com.example.app' \
      | zstd -3 --format=zstd -fo '…/1730000000000-apk_obb.tar.zst'
  tar -c -C /data/user/0 'com.example.app' \
      --exclude='com.example.app/lib' --exclude='com.example.app/oat' \
      --exclude='com.example.app/cache' --exclude='com.example.app/code_cache' \
      --exclude='com.example.app/no_backup' \
      | zstd -3 --format=zstd -fo '…/1730000000000-user.tar.zst'
  tar -c -C /data/user_de/0 'com.example.app' --exclude=… \
      | zstd -3 --format=zstd -fo '…/1730000000000-user_de.tar.zst'
  tar -c -C /storage/emulated/0/Android/data 'com.example.app' \
      --exclude='com.example.app/cache' \
      | zstd -3 --format=zstd -fo '…/1730000000000-data.tar.zst'
killall -s CONT com.example.app
# Java 侧随后用 FileSystemService 写 !BackupInfo!com.example.app.json
```

## 6. 引擎的隐含约束（重构必须对齐）

| 约束 | 后果 |
|---|---|
| 依赖 `killall`（busybox applet）停/继续进程 | 部分 ROM 上 `killall -s STOP` 可能失败（脚本容忍失败，但备份一致性下降） |
| tar 以「父目录 + 子名」方式打包 | 解包时必须 `-C <父目录>`，路径层级与包名强绑定，不能随意改包名恢复 |
| 备份时未记录 uid / SELinux 上下文 | 恢复时 uid 靠「现目录属主 / sdcardfs / packages.list」猜，SELinux 靠父目录上下文刷 —— **这是恢复失败的主要来源** |
| 分卷格式由扩展名决定，没有清单文件记录 | 如果用户改了扩展名，`parse_ext` 返回空 → 报「未知备份格式」 |
| 无校验和、无加密 | 传输损坏不可发现；备份明文可被任意 root 应用读取 |
| 时间戳做 CPId | 同一毫秒内重复备份会互相覆盖（实践中概率低） |
