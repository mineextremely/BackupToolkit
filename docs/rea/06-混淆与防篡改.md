# 06 · 混淆与防篡改

## 1. R8 重命名策略：用「Java 关键字」当标识符

这是本样本最显眼的特征：

- **包名**被改成 `abstract / break / case / … / while`、以及 `Activity / Intent / String / File / Service` 这类「看起来像系统类」的名字；
- **类名**被改成 `throw / while / import / public / static / native / …`；
- **字段/方法名**同样是关键字（dex 里真实存在 `break`、`default`、`return` 等方法名）。

后果：

1. Java 侧根本编译不过，`javac`/多数反编译器会直接崩或被扰乱；jadx 只能把它们改写成 `p000abstract.Cpublic`、`Cthrow`、`mo473break` 这类占位名 —— **读反编译结果时必须靠调用关系而不是名字来推理**；
2. `apktool` 的 smali 层**不受影响**（smali 允许任意 UTF-8 名称），所以 smali 是这类样本更可靠的交叉验证来源；
3. 重构时不要试图还原原始命名，直接按职责重写（本文档已给出职责映射，见 §4）。

## 2. 字符串加密（局部）

只有**一个类**用了字符串加密：`p004class.Cwhile`（root 服务的 `mo8continue`，即 JADX 语义名 `onBind`），解密器在基类 `p005const.Cthrow`：

```java
// 密钥在 Service 创建时确定
this.f1637extends = ((1047 ^ 1113) ^ getPackageName().length()) + 13;   // 1047/1113 = 版本号线索

public String m914true(char... cArr) {
    int n = cArr.length - 1;
    for (int i = 0; i < n; i++) cArr[i] = (char)(cArr[i] ^ this.f1637extends);  // 最后一个字符不参与异或
    return new String(cArr);
}
```

- 初始值 1047 在 `Activity.Cthrow.attachBaseContext()` 末尾通过虚调用 `p005const.Cthrow.mo13strictfp()` **运行时重算**：`1047 ^ 1113 = 78`；`78 ^ 14("r2ixzp.toolkit".length()) = 64`；`64 + 13 = 77` → **运行时密钥 = `'M'`**。
- `p004class.Cwhile.f665package = 77` 是另一个静态常量，门禁代码并不读它；密钥真正来自 `f1637extends`，不要写成「编译期常量折叠」。
- REA：`ev_3528c24f…`（`<init>` 置 1047）、`ev_0d4729e6…`（`mo13strictfp` 重算）、`ev_56a9bac3…`（`attachBaseContext` 虚调用）、`ev_da28a20e…`（解密器）。

**解出的全部字符串（12 条，可用 `re/scripts/decode_xor_strings.py` 复现）**：

| 解密结果 | 用途 |
|---|---|
| `getPackageManager` | 反射取 PM |
| `getPackageInfo` | 反射取 PackageInfo |
| `signatures` | 反射取签名字段 |
| `toByteArray` | 证书 DER |
| `java.security.MessageDigest` | 摘要算法 |
| `getInstance` | 反射 |
| `SHA-256` | 摘要算法名 |
| `update` | 反射 |
| `3SYJFfhhlM50hIfXHeeNP9p8Hjt8lNDfA5gsBXB3CGs=` | **期望的签名摘要（base64）** |
| `android.util.Base64` | 反射 |
| `encodeToString` | 反射 |
| `digest` | 反射 |

> 因为密钥里含 `getPackageName().length()`，**改包名必须重算所有密文字符**。本次样本的包名是 `r2ixzp.toolkit`（14 字符），密钥 77 与之自洽 —— 说明重打包者做了这一步。

## 3. 签名自校验门禁（Root 服务的「开关」）

`p004class.Cwhile.mo8continue()`（JADX 语义名 `onBind`；root 服务被实例化时执行）：

```java
IRootManager binder = null;
try {
    // 1) 取自身签名证书 DER
    Object pm   = getClass().getMethod("getPackageManager").invoke(this);
    Object pi   = pm.getClass().getMethod("getPackageInfo", String.class, int.class)
                    .invoke(pm, getPackageName(), 0);
    Object[] sigs = (Object[]) pi.getClass().getField("signatures").get(pi);
    byte[] der  = (byte[]) sigs[0].getClass().getMethod("toByteArray").invoke(sigs[0]);
    // 2) SHA-256 → Base64
    Object md = Class.forName("java.security.MessageDigest")
                    .getMethod("getInstance", String.class).invoke(null, "SHA-256");
    md.getClass().getMethod("update", byte[].class).invoke(md, der);
    byte[] dig = (byte[]) md.getClass().getMethod("digest").invoke(md);
    String b64 = (String) Class.forName("android.util.Base64")
                    .getMethod("encodeToString", byte[].class, int.class)
                    .invoke(null, dig, 2);
    // 3) 与内置常量比较，相等才创建 binder
    if ("3SYJFfhhlM50hIfXHeeNP9p8Hjt8lNDfA5gsBXB3CGs=".equals(b64)) {
        this.binder = new p004class.Cnative(this);
    }
} catch (Throwable ignored) { }
return this.binder;   // 校验失败 → 返回 null
```

验证：本 APK 证书 SHA-256

```
DD260915F86194CE748487D71DE78D3FDA7C1E3B7C94D0DF03982C057077086B
base64 = 3SYJFfhhlM50hIfXHeeNP9p8Hjt8lNDfA5gsBXB3CGs=      ← 与代码常量完全一致 ✅
```

**作用与影响**：

| 维度 | 说明 |
|---|---|
| 目的 | 防「重新签名后二次分发」——证书一变，root 服务不返回 binder，App 只能弹「Root服务启动失败」 |
| 实现位置 | 位于 **root 进程**（在 uid=0 的 `app_process` 里执行），不在 UI 进程，普通 Frida hook UI 进程无效 |
| 弱点 1 | 逻辑是纯 Java 反射 + 一次字符串比较，改动 `if` 条件或直接无条件 `new Cnative(this)` 即可绕过；也可直接改常量 |
| 弱点 2 | 校验失败只返回 null，**不主动退出/不擦数据**，对攻击者零成本 |
| 弱点 3 | 用 `android.util.Base64` 与 `MessageDigest` 都通过反射调用，规避了静态扫描对「签名校验」的字符串识别 |
| 佐证 | 该常量等于**分发者自己的证书**摘要 → 这正是「重签名 + 同步改常量」的证据（见 `01` §3） |

REA 证据：门禁方法 `ev_53ad62c5…`；空 binder 清理 `ev_bcd0b1f6…`（`m920extends(null)` 同时清空三个接口）；失败文案分支 `ev_f208157b…`；解密器 `ev_da28a20e…`。

## 5. 没有做的事（对重构是好事）

- ❌ 无壳 / 无 DEX 加密 / 无动态加载业务代码（`main.jar` 只是 libsu 的 root server，不是隐藏逻辑）
- ❌ 无 native 反调试、无 ptrace 检测、无模拟器检测
- ❌ 无 root 检测、无完整性校验（除上面那处签名比对）
- ❌ 无网络请求（连 `INTERNET` 权限都没有，「检查更新」只是打开浏览器）
- ❌ 无 SSL pinning、无设备指纹

⇒ 静态分析即可完整还原行为；重构时也**不需要**对抗这类保护。
