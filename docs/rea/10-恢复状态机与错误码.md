## 1. 不变量

| # | 不变量 | 对应缺陷 |
|---|---|---|
| R1 | **Commit 之前目标目录完全不动**；所有解包先到 staging | v1 直接解到目标父目录，失败留半残（`07` §2.3） |
| R2 | staging 与目标**同文件系统**，Commit 用 `rename` 而不是 copy | 跨 fs `mv` 退化为 copy，失败会留下半截（`07` §2.3） |
| R3 | 每个失败都必须有稳定 `code` + 明确 `dataState`；不允许「静默继续」 | v1 `mv`/`chown`/`restorecon` 失败静默（`07` §2.3） |
| R4 | `.bak` 只在 `Verify` 通过后才删除；删除失败不回滚、不丢 bak | 08 原写「Cleanup 失败则回滚」，会把已验证的成功恢复又撤掉 |
| R5 | 回滚幂等；回滚失败必须保留现场并报 `E_ROLLBACK_FAILED` | v1 回滚不检查返回值（`07` §2.3） |
| R6 | 清单是身份真值；只有 v1 才回退探测 uid/SELinux，并显式告警 | v1 三级猜测（`07` §2.1/2.2） |
| R7 | 归档**先校验后解包**，不信任扩展名/文件名/清单里的 `sha256` 以外的路径信息 | v1 以 root 解包外部可控 tar（`07` §3.2） |
| R8 | 取消只在安全点生效；Commit 开始后不中断 | 避免 rename 到一半 |
| R9 | 同一 `backup_home` 同时只允许一个恢复任务（锁） | 避免并发 rename |
| R10 | 崩溃后以 journal 为准；**不自动删 bak、不自动重试** | 断电/进程被杀后无法判断现场 |

## 2. 状态与阶段

### 2.1 状态图

```
Idle → Preflight → Prepare → Extract → Install → Commit → Verify → Cleanup → Done

失败去向：
  Preflight / Prepare / Extract   → Failed（目标数据未动；Extract 清理 staging）
  Install                         → Failed（数据未动，APK 可能已更新）
  Commit / Verify                 → Rollback → Failed（回滚成功）
  Rollback 自身失败               → Failed（E_ROLLBACK_FAILED，保留现场）

取消：Preflight/Prepare/Extract 以及 Install commit 前 → Cancelled；
      Install commit 后 / Commit / Verify → 延迟（W_CANCEL_DEFERRED）。
```

- `Install` 在「没有 `package` part 且目标已安装」时**跳过**，直接进入 `Commit`。
- `Rollback` 是独立状态，由 `Commit`/`Verify` 失败触发；用户取消不会进入 `Rollback`：Commit 前取消 → `Cancelled`，
  Commit 后取消 → `W_CANCEL_DEFERRED`。
- `Cancelled` 是终态；`Failed` 是终态；`Done` 是终态。

### 2.2 状态定义

| 状态 | 目的 | 入口条件 | 主要动作 | 成功出口 | 失败出口 |
|---|---|---|---|---|---|
| `Preflight` | 在不产生副作用的前提下证明「这次恢复可做」 | 有 `BackupSet`、锁已获取、用户已确认 | 校验清单/分卷/空间/目标包/签名/版本/用户/环境；写 journal | `Prepare` | `Failed`（目标未动） |
| `Prepare` | 准备 staging 与目标身份，停止应用 | Preflight 通过 | 解析目标路径与 uid（目标未安装且有 `package` part 时，uid 延迟到 Install 后解析）；创建 staging；`am force-stop`；确定 `.bak` 名 | `Extract` | `Failed`（清理 staging；stop 失败仅 `W_APP_LEFT_RUNNING`） |
| `Extract` | 解包并校验到 staging | Prepare 通过 | 逐 part 解压/校验；package 解到临时 APK 目录；进度/取消检查 | `Install`（有 package）或 `Commit` | `Failed`/`Cancelled`（清理 staging） |
| `Install` | 安装 APK（可选） | Extract 通过且有 `package` part，或目标未安装 | 校验 APK 签名；`pm install-create/write/commit`；校验安装结果；重查 uid | `Commit` | `Failed`（数据未动，APK 可能已更新） |
| `Commit` | 原子换名 + 属主/上下文 | Install 通过/跳过 | 逐 kind：`mv target bak` → `mv staging target` → `lib` 软链 → `chown` → `restorecon` | `Verify` | `Rollback` |
| `Verify` | 验证换名后的目标 | Commit 通过 | 抽查属主/上下文/关键文件/包版本/无 staging 残留/无 setuid | `Cleanup` | `Rollback` |
| `Cleanup` | 删除 bak/staging/临时 APK/journal | Verify 通过 | 删除；更新索引；释放锁 | `Done` | `Done` + `W_CLEANUP_INCOMPLETE` |
| `Rollback` | 把已 Commit 的 kind 反向恢复 | Commit/Verify 失败 | 逆序删除新目标、`mv bak target`；校验回滚结果；删除 staging/临时（失败只告警） | `Failed`（`rolledBack=true`） | `Failed`（`E_ROLLBACK_FAILED`） |
| `Done` | 成功终态 | Cleanup 完成 | 释放锁；更新索引 | — | — |
| `Failed` | 失败终态 | 任意 fatal | 释放锁；保留 journal/bak（如有） | — | — |
| `Cancelled` | 取消终态 | Commit 前取消 | 清理 staging/临时 APK；释放锁 | — | — |

## 3. 状态迁移表

| # | From | 事件 / 守卫 | To | 动作 / 副作用 |
|---|---|---|---|---|
| 1 | `Idle` | `START`；用户确认；锁获取成功 | `Preflight` | 生成 `restoreId`；写 journal（`phase=Preflight`） |
| 2 | `Preflight` | 全部检查通过 | `Prepare` | journal.phase=Prepare |
| 3 | `Preflight` | 任一 fatal；或用户取消 | `Failed` / `Cancelled` | 无目标副作用；写错误 |
| 4 | `Prepare` | staging 创建成功；`force-stop` 失败 → `W_APP_LEFT_RUNNING`，继续 | `Extract` | journal.paths/staging/uid 落盘 |
| 5 | `Prepare` | staging 创建失败 / 目标父目录不存在 / 空间在创建后不足 | `Failed` | 删除 staging；app 可能已停止 |
| 6 | `Extract` | 所有选中 kind 解包 + 校验通过；未取消 | `Install`（有 package） | 记录 `extractedKinds` |
| 7 | `Extract` | 同上，但没有 package part | `Commit` | 同上 |
| 8 | `Extract` | 归档不安全/损坏/超限/IO/取消 | `Failed` / `Cancelled` | 删除 staging + 临时 APK；目标未动 |
| 9 | `Install` | `pm install-commit` 成功且校验通过 | `Commit` | 重查目标 uid/appId；journal.installed=true |
| 10 | `Install` | session/write/commit/verify 失败 | `Failed` | `pm install-abandon`（若 session 还在）；删临时；数据未动；APK 可能已更新 |
| 11 | `Install` | 跳过（无 package part） | `Commit` | 无 |
| 12 | `Commit` | 所有选中数据 kind 换名/属主/上下文成功 | `Verify` | 记录 `committed[]` 与每个 bak |
| 13 | `Commit` | 任一 kind 失败 | `Rollback` | 保留已完成 kind 的 bak；当前 kind 按 §5.2 回滚 |
| 14 | `Verify` | 全部检查通过 | `Cleanup` | journal.phase=Cleanup |
| 15 | `Verify` | 任一检查失败 | `Rollback` | 不删 bak |
| 16 | `Cleanup` | bak/staging/temp 全部删除 | `Done` | 更新 index；释放锁 |
| 17 | `Cleanup` | 部分删除失败 | `Done` | `W_CLEANUP_INCOMPLETE`；保留路径并展示 |
| 18 | 任意 `Preflight`/`Prepare`/`Extract` | `CANCEL` | `Cancelled` | 删除 staging/临时；`E_CANCELLED`（info） |
| 19 | `Install`（commit 前） | `CANCEL` | `Cancelled` | `install-abandon`；删临时；数据未动 |
| 20 | `Install`（commit 后）/`Commit`/`Verify` | `CANCEL` | 不变 | `W_CANCEL_DEFERRED`；继续到 Done/失败 |
| 21 | `Rollback` | 全部反向恢复成功 | `Failed` | `rolledBack=true`；`dataState=target_untouched`（旧数据已回） |
| 22 | `Rollback` | 任一步失败 | `Failed` | `E_ROLLBACK_FAILED`；保留 target/bak；`dataState=rollback_failed` |
| 23 | 任意 | 进程崩溃/被杀 | （重启后 `Recovery` 例程） | 读 journal，按 §6.3 选择完成/回滚；不自动重试 |

## 4. 失败矩阵

| 状态 | 典型失败 | 目标数据 | `.bak` | staging | 去向 | 最终 `dataState` |
|---|---|---|---|---|---|---|
| `Preflight` | 清单/哈希/空间/签名/版本/环境 | 未动 | 无 | 无 | `Failed` | `target_untouched` |
| `Prepare` | staging 创建失败、父目录缺失、uid 解析失败 | 未动 | 无 | 可能已建 | `Failed` | `target_untouched` |
| `Extract` | 归档逃逸/损坏/超限/空间/IO/取消 | 未动 | 无 | 部分 | `Failed`/`Cancelled` | `target_untouched` |
| `Install` | session/write/commit/verify 失败 | 未动 | 无 | 完整 | `Failed` | `installed_data_old`（APK 可能已更新） |
| `Commit` | `mv`/`chown`/`restorecon`/`lib` 失败 | 可能部分已换名 | 有 | 部分 | `Rollback` | `target_replaced` → 回滚后 `target_untouched` |
| `Verify` | 属主/上下文/版本/残留检查失败 | 已换名 | 有 | 无 | `Rollback` | 同上 |
| `Cleanup` | 删除 bak/staging 失败 | 已是新数据 | 可能保留 | 无 | `Done` | `restored_with_bak`（+告警） |
| `Rollback` | 删除新目标/恢复 bak 失败 | 不确定 | 有 | 无 | `Failed` | `rollback_failed` |

> `installed_data_old` 的含义：APK 已被替换/安装，但用户数据仍是旧的。这不是「数据丢失」，但**不是原子成功**；
> UI 必须明确显示「应用已更新，数据未恢复」，并提供「重试恢复数据」入口。

## 5. Commit / Rollback 协议

### 5.1 staging 位置

staging 必须是目标的**兄弟目录**，保证同一文件系统；不要用 `/data/local/tmp` 放用户数据
（`/data/local/tmp` 与 `/data/user` 通常同一分区，但与 `/sdcard` 的 FUSE 视图不保证 rename 语义）。

| kind | 目标 | staging（`<restoreId>` 替换） |
|---|---|---|
| `package` | 不落用户目录 | `/data/local/tmp/toolkit-<restoreId>/apk/`（只放临时 APK） |
| `apk_obb` | `<sd>/Android/obb/<pkg>` | `<sd>/Android/obb/.toolkit-staging-<restoreId>/<pkg>` |
| `internal_data` | `/data/user/<targetUserId>/<pkg>` | `/data/user/<targetUserId>/.toolkit-staging-<restoreId>/<pkg>` |
| `internal_device_protected` | `/data/user_de/<targetUserId>/<pkg>` | `/data/user_de/<targetUserId>/.toolkit-staging-<restoreId>/<pkg>` |
| `external_data` | `<sd>/Android/data/<pkg>` | `<sd>/Android/data/.toolkit-staging-<restoreId>/<pkg>` |

说明：

- v1 的归档是 `tar -C <父目录> <pkg>`，所以解包时 `-C <staging 父目录>` 会自然得到 `<staging>/<pkg>`，
  再 `mv <staging>/<pkg> <target>`；不要解到 `<staging>/` 里面再套一层。
- `<sd>` 对 0 号用户是 `/sdcard` 的真实路径；对其他用户是 `/data/media/<targetUserId>/Android`（O：`03` §3.3）。
- `/data/local/tmp` 不可写/不可用时，`package` 临时目录退化到 `<app files>/cache/toolkit-<restoreId>/`
  （root 可访问；清理时一并删除）。
- staging 目录用 `0700`；完成后删除；崩溃遗留由 journal/启动清理处理。
- 同 fs 校验：`mv` 返回 `EXDEV` → `E_STAGING_NOT_SAME_FS`；不要退回 `cp -r`（会破坏原子性）。

### 5.2 单个 kind 的换名序列

```
target = ...; stagingPkg = <staging>/<pkg>
bak = <target 父目录>/.toolkit-bak-<restoreId>-<kind>   # 隐藏兄弟目录，避免包名过长/被扫描

1. if target exists:
     mv target bak              # 失败 → E_MV_FAILED；target 未动，直接中止该 kind
2. mv stagingPkg target         # 失败 → 若有 bak，mv bak target；E_MV_FAILED；中止
3. if internal kind:
     ensure_lib_symlink(target, uid, pkg)  # 失败 → 移除 target，恢复 bak；E_IO
     chown -hR <uid>:<uid> target          # 失败 → 移除 target，恢复 bak；E_CHOWN_FAILED
     restorecon -RF target                 # 失败/类型不符 → 见 §5.4；E_SELINUX_FAILED
4. 记录 committed += {kind, target, bak, hadTarget}
```

- `mv target bak` 必须检查返回码；v1 的 `2>/dev/null` 静默失败是**禁止照抄**的（`07` §2.3）。
- `bak` 名冲突时追加 `-2`、`-3`；不得覆盖已有 bak。使用隐藏兄弟目录（`.toolkit-bak-…`）而不是
  `<target>.bak`，避免包名过长超过文件名上限，也避免被媒体扫描/应用看到。
- `target` 必须是目录；若是符号链接/文件 → `E_MV_FAILED`（不跟随）。
- `chown` 的 gid 用 uid（Android 上应用 uid==gid；O：`03` §3.7）。
- `chown -hR` 只对内部 kind；`external_data`/`apk_obb` 在 FUSE 上不做 `chown`（做了也可能失败/无意义）。
- `restorecon` 只对内部 kind；共享存储不做（与 v1 的 `restore data` 不 `recon` 一致，O：`03` §3.3/§3.7）。
- `lib` 软链：v1 在恢复前记住旧 `lib` 的真实路径，解包后重建（O：`03` §3.8）。v2 优先在安装后通过
  `ApplicationInfo.nativeLibraryDir` 取当前真实路径；取不到时才回退到「换名前 `readlink target/lib`」的值。
  `lib` 不进入 tar（v1 已排除，O：`03` §3.3）。软链必须在 `chown`/`restorecon` **之前**创建，
  这样新链接也会被覆盖；`nativeLibraryDir` 为空时跳过。

### 5.3 多 kind 的提交顺序与回滚

- 提交顺序（从「较不重要/可重建」到「最重要」）：
  `apk_obb` → `external_data` → `internal_device_protected` → `internal_data`。
- 任一步失败：按 `committed[]` **逆序**回滚；当前 kind 按 §5.2 局部回滚。
- 所有 kind 都成功后，才进入 `Verify`；`Verify` 失败也按 `committed[]` 逆序回滚。
- `Rollback` 不得删除 `bak`，直到回滚成功；回滚失败时**保留 target + bak**，并写 journal。
- 回滚成功后，`bak` 已被 `mv` 回 target，不需要再删；`Rollback` 负责删除 staging/临时 APK，
  删除失败只报 `W_CLEANUP_INCOMPLETE`，不改变 `rolledBack=true`。

### 5.4 SELinux 处理

```
restorecon -RF <target>
if success:
    actualType = ls -Z <target> | awk '{print $1}' | strip ':c*'
    if manifest.selinux.dataType != null and actualType != dataType:
        E_SELINUX_FAILED           # 策略/路径不匹配，回滚
    else:
        ok                          # 类别由系统策略决定
else if manifest.selinux.dataContext != null and targetUserId == source.userId:
    chcon -hR <dataContext> <target> # 同用户才可用完整上下文；-h 不跟随 symlink
    W_SELINUX_DEGRADED
else if manifest.selinux.dataType != null:
    chcon -hR <dataType> <target>    # 跨用户只用类型级
    W_SELINUX_DEGRADED
else:
    W_SELINUX_UNVERIFIED            # 没有上下文信息，无法验证
    if !allowUnverifiedSelinux: E_SELINUX_FAILED
```

要点：

1. **不再使用父目录上下文**（v1 的 `ls -Z` 父目录 + 剥 `:c*` 是 `07` §2.2 的根因）；
2. `restorecon -F` 是首选；`chcon` 只是降级；
3. 跨用户绝不照搬 `:c512,c768` 之类的 MLS 类别；
4. `allowUnverifiedSelinux` 默认 **false**：无法验证时回滚，避免「恢复成功但应用闪退」；
5. `external_data`/`apk_obb` 跳过本节；
6. `chcon` 一律用 `-hR`（不跟随 symlink）；`restorecon` 用 `-RF`（递归）；验证至少抽查 target 根与 2–3 个子目录，
   不能只验根目录。
7. 两条 `chcon` 路径都必须检查退出码；失败 → `E_SELINUX_FAILED`（`allowUnverifiedSelinux=true` 时才降级为
   `W_SELINUX_UNVERIFIED` 并继续）。

### 5.5 APK 安装与「不可回滚性」

- 安装前校验：`package` part 的归档形状是扁平 `*.apk`；必须有 `base.apk`；拒绝符号链接/子目录；
  用 `PackageManager.getPackageArchiveInfo(baseApk, GET_SIGNING_CERTIFICATES)` 计算证书 SHA-256
  （API < 28 用 `GET_SIGNATURES` 后取 `toByteArray()`）；与 `manifest.package.signerSha256` 比对；
  v1 为 `null` → `W_SIGNER_UNVERIFIED`。
- 安装命令（v2 默认）：
  - 不伪造来源：**去掉** `-i com.android.vending`（`07` §3.4）；
  - 不改全局设置：**不做** `settings put global…`（`07` §3.4）；
  - 默认不带 `--bypass-low-target-sdk-block`；只有 `compatInstall=true` 且 SDK≥34 才加；
  - 降级：只有 `allowDowngrade=true` 才加 `-d`，否则预检 `E_VERSION_DOWNGRADE_BLOCKED`；
  - 单 APK：`pm install -r -t [--user <uid>]`；多 APK：`pm install-create` → `install-write -S` →
    `install-commit`；任一步失败都 `install-abandon`。`install-create` 成功后把 session id 写进
    `journal.pmSession`，commit/abandon 后清空（崩溃恢复用）。
- 安装后校验：`pm path --user <uid> <pkg>` 存在；`dumpsys package` 的 `versionCode` 等于清单
  （若恢复的是 package part）；否则 `E_INSTALL_VERIFY`。
- 安装后重查 uid/appId：若清单 `appId` 非空且与目标不一致：
  - 默认 `E_UID_MISMATCH`（数据尚未 Commit，目标未动；APK 可能已更新）；
  - 只有 `allowUidRemap=true` 才继续，并用**目标实际 uid**做 `chown`。
- **APK 不回滚**：`pm` 没有事务性「恢复旧 APK」；v2.0 明确不做自动 APK 回滚。
  若 `Install` 成功而后续失败，`dataState=installed_data_old`，UI 提供「重试数据恢复」；
  可选「安装前快照当前 APK 集」见 U1。
- `Install` 之前是否 `force-stop`：`Prepare` 已做；`pm install` 对已运行应用会杀进程，无需重复。

### 5.6 Verify 清单

| 检查 | 内部 kind | 外部 kind |
|---|---|---|
| 目标目录存在、是目录、非符号链接 | 是 | 是 |
| `stat` uid/gid == 目标 uid | 是 | 否（FUSE） |
| `ls -Z` 类型 == `selinux.dataType`（若已知） | 是 | 否 |
| 关键文件存在（如 `shared_prefs/`、`databases/` 至少一个；没有则跳过） | 是 | 是 |
| 无 `.toolkit-staging-*` 残留 | 是 | 是 |
| 无 setuid/setgid 文件 | 是 | 是 |
| `lib` 软链（若有 native lib）可解析 | 是 | 否 |
| 包已安装、`versionCode` 符合预期 | package | — |
| 可选：`pm resolve-activity` 能解析启动 Intent | package | — |

`Verify` **不启动应用**（避免副作用/ANR）；「能否启动」属于可选软校验（U6）。

## 6. 取消、journal 与崩溃恢复

### 6.1 取消点

取消标志：`<home>/.toolkit/cancel/<taskId>`（存在即取消）或 journal 的 `cancelRequested=true`。
shell 在安全点检查；UI 不直接 `kill -9`（会留半截）。

| 阶段 | 是否可取消 | 行为 |
|---|---|---|
| `Preflight` | 是 | 直接 `Cancelled`；无副作用 |
| `Prepare` | 是 | 删 staging；`Cancelled`；app 可能已 stop（不自动重启） |
| `Extract` | 是（每个 part / 每 N 个条目） | 删 staging/临时；`Cancelled` |
| `Install`（commit 前） | 是 | `install-abandon`；删临时；`Cancelled` |
| `Install`（commit 后） | 否 | `W_CANCEL_DEFERRED`；继续 |
| `Commit` / `Verify` | 否 | `W_CANCEL_DEFERRED`；继续到 Done/失败 |
| `Cleanup` | 是（无实际作用） | 完成清理；`Done` |

最终 `status=cancelled` 时错误码用 `E_CANCELLED`（severity=info），不要当失败弹窗。

### 6.2 journal

路径：`<home>/.toolkit/journal/<restoreId>.json`（原子写：tmp + rename + fsync）。

```json
{
  "schema": 1,
  "restoreId": "1792382400000-3f9a1c2d-9f3a1c2d",
  "backupId": "1792382400000-3f9a1c2d",
  "pkg": "com.example.app",
  "targetUserId": 0,
  "phase": "Commit",
  "status": "running",
  "createdAt": "2026-10-19T05:00:00.000Z",
  "updatedAt": "2026-10-19T05:01:00.000Z",
  "paths": {
    "stagingRoots": [
      "/data/user/0/.toolkit-staging-…",
      "/sdcard/Android/data/.toolkit-staging-…"
    ],
    "current": {
      "target": "/data/user/0/com.example.app",
      "bak": "/data/user/0/.toolkit-bak-…-internal_data"
    },
    "tempApk": "/data/local/tmp/toolkit-…/apk"
  },
  "uid": 10123,
  "selinux": { "dataType": "u:object_r:app_data_file:s0" },
  "extractedKinds": ["package", "internal_data"],
  "installed": true,
  "pmSession": null,
  "committed": [
    { "kind": "internal_data", "target": "…", "bak": "…", "hadTarget": true }
  ],
  "cancelRequested": false,
  "error": null
}
```

规则：

- `phase` 与 §2.2 状态同名；`status ∈ running|done|failed|rolled_back|cancelled|interrupted`；
- 每次状态迁移都先更新 journal，再执行副作用；
- `paths.stagingRoots` 记录所有已创建的 staging 父目录（跨内部/共享存储）；`paths.current` 是当前 Commit 的
  kind 的 target/bak；`committed[]` 保存已提交的每个 kind（Recovery 逆序回滚用）；`pmSession` 在
  `install-create` 成功后写入，`install-commit`/`install-abandon` 后清空；
- `paths` 只写绝对路径；导出诊断时脱敏；
- journal 损坏 → `E_JOURNAL_CORRUPT`；UI 展示路径，允许手动处理，不自动删任何东西。

### 6.3 启动时恢复（Recovery）

启动/打开恢复页时扫描 `status=running` 的 journal：

| journal.phase | 现场 | 默认动作 | 可选动作 |
|---|---|---|---|
| `Preflight`/`Prepare`/`Extract` | 目标未动；staging 可能残留 | 删除 staging/临时；标记 `interrupted`；提示「上次恢复未完成，数据未变」 | 重试 |
| `Install` | APK 可能已更新；session 可能未关 | 尝试 `pm install-abandon`（若 session id 还在）；标记 `interrupted`；数据未动 | 重试数据恢复 |
| `Commit`/`Verify` | target 与 bak 可能同时存在 | **默认回滚**：删新 target、`mv bak target`；标记 `rolled_back` | 若 Verify 已通过，可选「完成清理」（保留新数据） |
| `Cleanup` | 新数据已验证；bak 可能残留 | 完成删除 bak/staging；标记 `done` | 保留 bak |
| `Rollback` | 回滚可能中断 | 继续回滚；失败 → `E_ROLLBACK_FAILED`，保留现场 | 手动 |

原则：**不自动 resume 到一半的 Extract**；不自动删除 bak；不回滚未确认的 `Cleanup` 状态（可能已成功）。

## 7. 归档条目安全校验

### 7.1 规则（任何一条不满足 → `E_ARCHIVE_UNSAFE`）

| 规则 | 说明 |
|---|---|
| 路径必须相对 | 拒绝 `/` 开头、Windows 盘符、UNC；允许开头的 `./`，规范化后再校验 |
| 禁止 `..` 段 | 拒绝 `a/../b`、`..`、`a/..` |
| 禁止控制字符 | NUL、换行、`\r`、`\t`、`\u0000-\u001f`、`\u007f` |
| 禁止反斜杠 | `\` 在 Android 上是合法文件名字符，但容易造成跨平台歧义；拒绝 |
| 类型白名单 | 只允许 regular / dir / symlink / hardlink；拒绝 char/block/fifo/socket；未知 typeflag（含 GNU sparse `S`）→ 拒绝（fail-closed） |
| symlink 目标 | 必须是相对路径；按链接父目录词法规约后必须仍在 staging 内（允许安全的 `..`，拒绝逃逸）；不得指向另一个 symlink 造成逃逸链 |
| hardlink 目标 | 必须是归档内已出现的 regular entry，且词法规约后在 staging 内 |
| 重复路径 | 拒绝同名条目（含大小写不敏感重复，针对 FAT/exFAT 目标） |
| 路径长度 | ≤4096 字节；单段 ≤255 |
| 条目数 | ≤ `entryCount`（若清单有）×1.02+1024，且 ≤1,000,000 |
| 解压总量 | ≤ `uncompressedBytes`（若清单有）×1.02+64 MiB；且 ≤ 目标 fs 可用空间；若清单**没有** `uncompressedBytes`，则压缩比 >100:1 拒绝（zip bomb）。清单值本身不可信，实际解压超过声明值时立即中止 |
| 归档形状 | `package`：顶层只能有 `*.apk` 平铺；其余 kind：顶层必须是 `<pkg>/`（§7.2） |
| setuid/setgid | 解包后扫描并清除（`chmod ug-s`）；不拒绝（应用可能需要可执行位，但不需要 suid） |

### 7.2 归档形状

| kind | 允许的顶层条目 | 例子 |
|---|---|---|
| `package` | `base.apk`、`split_*.apk` 等**平铺文件**；不允许目录 | `base.apk` |
| `apk_obb` | 只有 `<pkg>/`（目录）及其子树 | `com.example.app/` |
| `internal_data` | 只有 `<pkg>/` | `com.example.app/shared_prefs/…` |
| `internal_device_protected` | 只有 `<pkg>/` | `com.example.app/…` |
| `external_data` | 只有 `<pkg>/` | `com.example.app/files/…` |

> 这条直接把「把任意路径塞进 tar」挡在解包前；v1 的 `decompress` 完全不做（`07` §3.2）。

### 7.3 两阶段校验（关键）

1. **Pass 1：解析 tar 头，不落盘**
   - 不能依赖 `tar -tv`/`tar -tf` 的文本输出：文件名里的换行/控制字符可以伪造列表；
   - 必须按 512 字节 tar header 解析 `name`/`prefix`/`typeflag`/`size`/`linkname`，并处理 GNU longname（`L`/`K`）
     与 pax（`x`/`g`）扩展头；
   - 对每个条目做 §7.1 校验；同时模拟目录树，记录 symlink 目标，拒绝「后续条目穿过 symlink」；
   - 累计条目数/解压字节数，检查上限。
2. **Pass 2：解包**
   - 解到**空的** staging；`tar -x -C <staging> -o`（`-o` = 不恢复归档属主；不要 `-p`）；
   - **禁止跟随 symlink**：优先逐条目解包（`openat`/`O_NOFOLLOW`），或使用已确认不会跟随 symlink 的 tar 实现；
     不能假定 busybox/GNU tar 在所有 ROM 上的行为一致；
   - 解包过程中再次检查条目（防止 Pass 1/Pass 2 之间的 TOCTOU；归档文件本身是只读的，但仍建议）；
   - 解包后扫描：`find -type l` 校验所有链接；`find -perm /6000` 清 suid；`du` 对比 `uncompressedBytes`；
   - 任何失败都删除 staging，目标未动。

> 两次解压的 CPU 成本可接受；安全优先。若实现选择「边解边校验」，必须使用严格的流式 tar 解析器，
> 不能退回 `tar -tv` 文本解析。

### 7.4 v1 备份同样要过校验

v1 的 `decompress` 没有校验（`07` §3.2），所以**即使恢复 v1 备份也必须执行 §7.1–§7.3**。
v1 没有 `sha256` 只影响完整性（`W_HASH_UNVERIFIED`），不影响安全性校验。

## 8. 错误码

### 8.1 约定

- `E_` = error/fatal；`W_` = warning；`E_CANCELLED` 是 info 级终态。
- 错误码**稳定、不复用**；新增只追加；UI 用代码做本地化，日志保留英文 message。
- 每个错误事件必须带：`code`、`phase`、`severity`、`retryable`、`dataState`。
- `dataState` 枚举：`target_untouched` / `staging_only` / `target_replaced` / `installed_data_old` /

### 8.3 事件 JSON

```json
{
  "v": 1,
  "ts": 1792382601123,
  "taskId": "1792382400000-3f9a1c2d-9f3a1c2d",
  "phase": "Extract",
  "event": "error",
  "code": "E_ARCHIVE_UNSAFE",
  "kind": "internal_data",
  "severity": "fatal",
  "retryable": false,
  "dataState": "target_untouched",
  "message": "archive entry escapes staging root",
  "detail": { "entry": "../etc/passwd" },
  "progress": { "done": 1, "total": 3, "bytes": 12345678 }
}
```

- `detail` 只放诊断所需的最小信息；**不要放用户文件内容/密钥**；
- `message` 英文、可读；UI 用 `code` 本地化；
- `progress` 可选；`done/total` 以 part 为单位，`bytes` 为当前 part 已处理字节（估算可）。

### 8.4 shell 事件行与退出码

libsu 的命令通道只回传文本 + 退出码；v2 的 shell 侧输出**结构化事件行**，不要用自然语言解析：

```
EVT|v=1|ts=<epochMillis>|task=<taskId>|phase=<state>|event=<start|progress|end|error>|code=<CODE>|kind=<kind|->|done=<n>|total=<n>|bytes=<n>
```

- 所有值限制在 `[A-Za-z0-9_.:-]`；`taskId`/`kind`/`CODE` 本身满足；不写路径/备注；
- 人类可读日志另走日志文件；

## 9. 验收用例

| # | 场景 | 期望 |
|---|---|---|
| T1 | v2 `complete` 正常恢复 | `Done`；target 新数据；bak 删除；无 staging |

| T3 | part sha256 不符 | `E_PART_HASH_MISMATCH`；target 未动 |
| T4 | tar 条目 `../x` | `E_ARCHIVE_UNSAFE`；target 未动；staging 删除 |
| T5 | tar 绝对路径 `/data/...` | `E_ARCHIVE_UNSAFE` |
| T6 | symlink 指向 `/data/user/0/other` | `E_ARCHIVE_UNSAFE` |
| T7 | hardlink 指向归档外 | `E_ARCHIVE_UNSAFE` |
| T8 | 设备文件/管道 | `E_ARCHIVE_UNSAFE` |
| T9 | 条目数/解压量超限 | `E_ARCHIVE_LIMIT` |
| T10 | `package` 归档含子目录 | `E_ARCHIVE_UNSAFE` |
| T11 | 非 `package` 归档顶层不是 `<pkg>/` | `E_ARCHIVE_UNSAFE` |
| T12 | 空间不足（new+old+slack） | Preflight `E_SPACE`；target 未动 |
| T13 | 目标未安装、只选数据、无 package | `E_TARGET_NOT_INSTALLED` |
| T14 | 签名不符 | `E_SIGNER_MISMATCH`；不安装 |
| T15 | 降级未允许 | `E_VERSION_DOWNGRADE_BLOCKED` |

| T18 | Commit 中 `mv target bak` 失败 | `E_MV_FAILED`；target 未动；staging 清理 |
| T19 | Commit 中 `mv staging target` 失败 | 恢复 bak；`E_MV_FAILED`；target 旧数据 |
| T20 | `chown` 失败 | 回滚；`E_CHOWN_FAILED`；target 旧数据 |
| T21 | `restorecon` 失败/类型不符 | 回滚；`E_SELINUX_FAILED` |
| T22 | Verify 失败 | 回滚；`E_VERIFY_FAILED` |
| T23 | 回滚失败 | `E_ROLLBACK_FAILED`；target+bak 保留 |
| T24 | Cleanup 删 bak 失败 | `Done` + `W_CLEANUP_INCOMPLETE`；bak 保留 |

| T26 | 取消于 Install commit 前 | `Cancelled`；session abandon；数据未动 |
| T27 | 取消于 Commit | `W_CANCEL_DEFERRED`；最终 Done |
| T28 | 崩溃于 Extract 后 | Recovery 删 staging；`interrupted`；target 未动 |
| T29 | 崩溃于 Commit | Recovery 默认回滚；`rolled_back` |
| T30 | 崩溃于 Verify 后 Cleanup 前 | Recovery 完成清理或保留 bak；不丢新数据 |
| T31 | v1 appdir 备份恢复 | `W_LEGACY_FORMAT`/`W_HASH_UNVERIFIED`/`W_SIGNER_UNVERIFIED`；仍做安全校验 |

## 10. 与 `08` 的差异 / 修订记录

| 08 原文 | 本文修订 | 原因 |
|---|---|---|
| 只有 7 个状态，没有终态/回滚状态 | 明确 `Done`/`Failed`/`Cancelled`/`Rollback`，并增加 `Recovery` 例程 | 失败/取消/崩溃必须有确定落点 |
| `Cleanup → 删除 .bak；失败则回滚 rename` | **Cleanup 删除失败不回滚**；保留 bak + `W_CLEANUP_INCOMPLETE` | Verify 已通过，回滚会毁掉成功恢复 |
| `Install 失败 → 整体放弃` | 区分为「数据未动 + APK 可能已更新」；`dataState=installed_data_old` | `pm` 无事务回滚，必须如实告知 |
| `Commit → 目标 rename 为 .bak；staging rename；chown；restorecon` | 细化顺序、同 fs 约束、逐 kind 回滚、`lib` 软链、SELinux 回退 | 可直接实现/测试 |
| `uid/SELinux 只信清单` | uid 用 `userId*100000+appId`；SELinux 优先 `restorecon`，清单只做校验/降级 | 跨用户类别不可照搬；restorecon 才是策略真值 |
| 取消标志文件，tar 每处理一个 part 检查 | 明确取消点表；Install commit 后/Commit 不可取消 | 避免 rename 中断 |
| 错误码只列了 4 个 | 完整 40+ 稳定错误码 + 退出码 + v1 输出映射 | UI/日志/测试需要 |
| 归档校验只写「拒绝绝对路径/../symlink」 | 增加 tar 头解析、形状校验、条目数/解压量上限、两阶段 | 文本 `tar -tv` 可被换行文件名绕过 |
| 未提 journal/崩溃恢复 | 增加 journal schema + 启动恢复表 | 断电/进程被杀是常态 |
