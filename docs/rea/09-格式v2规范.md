## 0. 范围与术语

**范围**

- v2 的目录布局、清单 schema、分卷元数据、哈希与原子写协议；
- v1 → v2 的**只读适配器**与显式迁移；
- 格式版本演进规则。

**不在本文**

- 恢复算法、状态迁移、回滚与错误码 → `10`；
- UI/交互与进度展示 → `08` §7；
- 实现代码、Gradle 模块、脚本 → 后续里程碑（`08` §9）。

**术语**

| 术语 | 含义 |
|---|---|
| `BackupSet` | 一次备份在内存中的完整描述；来自 v2 `manifest.json`，或由 v1 适配器合成 |
| `manifest` | 单次备份的 `manifest.json`，格式的**唯一真值** |
| `part` | 一个分卷文件（如 `internal_data.tar.zst`） |
| `kind` | 分卷的语义类型（如 `internal_data`），取代 v1 的 `user`/`data`/`apk` |
| `mode` | 用户可见的三档选择（`apk`/`user`/`data`），与 v1 UI 对齐；一个 mode 会展开成多个 `kind` |
| `backupId` | 一次备份的不可变 id，同时是目录名 |
| `restoreId` | 一次恢复任务的 id（`<backupId>-<8 hex>`），用于 staging/journal/`.bak` 命名 |
| `sourceKey` | v1 迁移的幂等键，标识「哪个 v1 备份被迁移过」 |

## 1. 设计不变量

| # | 不变量 | 理由 / 对应缺陷 |
|---|---|---|
| I1 | **清单是唯一真值**；文件名、扩展名、目录名只作提示 | v1 用文件名正则推断档位与格式，改名即失效（`04` §3、§6） |
| I2 | 每个 part 必须记录 `sha256` + `sizeBytes`；清单自描述 `compression`/`level` | v1 无校验、无格式记录（`07` §2.5、§3.1） |
| I3 | 恢复所需的身份信息在备份时快照：`pkg`、`appId`、`userId`、`signerSha256`、`selinux.dataType` | v1 恢复时猜 uid/SELinux（`07` §2.1、§2.2） |
| I4 | 清单与分卷的落盘是**原子**的（临时文件 + rename）；中断可识别 | v1 的 JSON 与分卷是两套真值（`04` §6） |
| I5 | v2 **只写新布局**；v1 只读；迁移必须显式、幂等、可中断 | 避免误改老备份（`08` §4.3） |
| I6 | 未知字段忽略；未知 `kind` 跳过并告警；`schema` 主版本不兼容则拒绝 | 为 v2.x 留演进空间 |
| I7 | `parts[].file` 必须是**相对 basename**，不得含 `/`、`..`、控制字符 | 防止清单本身变成路径逃逸入口 |
| I8 | 时间统一 UTC RFC 3339；`backupId` 文件安全且可按字典序近似按时间排序 | 多设备/时区/排序一致性 |
| I9 | `uid = userId × 100000 + appId`，**算术计算**，不用字符串拼接 | v1 `USER_ID$appid` 在 `appId < 10000` 且 `userId > 0` 时会错（§5.5） |
| I10 | 完整 SELinux MLS 类别（`:c512,c768`）只对**同一用户**有意义；跨用户只用 `dataType` + `restorecon` | 类别由策略按用户/路径分配（`07` §2.2） |
| I11 | v2 不写 `!BackupInfo!<pkg>.json`，也不依赖 `config.json`；老 App 看不到 v2 备份 | 双格式共存，避免互相破坏 |
| I12 | 一个 `backup_home` 同时只允许一个写任务/恢复任务（锁文件） | 避免并发 rename/清理互相踩踏 |

## 2. 目录布局

### 2.1 根目录

```
<backup_home>/
├── .nomedia                      # 防止媒体扫描（v1 已有，O）
├── toolkit.json                  # 备份根元数据（v2 新增；替代 v1 config.json 的角色）
├── apps/
│   └── <pkg>/
│       ├── index.json            # 该应用备份列表的**派生缓存**（可重建，非真值）
│       ├── icon.png              # 可选；v1 的 !icon!<pkg> 对应物
│       └── <backupId>/
│           ├── manifest.json     # 单次备份的完整清单（唯一真值）
│           ├── package.tar.zst
│           ├── apk_obb.tar.zst
│           ├── internal_data.tar.zst
│           ├── internal_device_protected.tar.zst
│           └── external_data.tar.zst
├── self/
│   └── BackupToolkit-<versionCode>.apk  # 当前版本自身备份（可选；只保留当前版本）
└── .toolkit/                     # 运行时状态，不属于备份数据
    ├── journal/                  # 恢复日志（见 10 §6）
    ├── cancel/                   # 取消标志
    └── lock                      # 单任务锁
```

要点：

- `apps/<pkg>/index.json` 只是缓存；**恢复永远只读 `<backupId>/manifest.json`**。索引丢失/过期时扫描
  `*/manifest.json` 重建（`W_INDEX_STALE`）。
- `.toolkit/` 可以被安全删除（会丢失未完成任务的恢复线索，见 `10` §6.3）。
- `icon.png` 不参与恢复正确性；写入失败只告警。
- `self/` 只保留当前版本的 `BackupToolkit-<versionCode>.apk`；写新成功后删除旧 v2 self 文件；
  **不写、不改 v1 的 `!app!.apk`**。`toolkit.json.selfBackup` 记录当前 self 的元数据（见 §3.1）。
- `toolkit.json` 缺失时按「空根」初始化；`schema > 2` 时**拒绝写入**（避免新版本写坏旧实现）。

### 2.2 命名规则

| 对象 | 规则 | 示例 |
|---|---|---|
| `backupId`（v2 生成） | `<epochMillis>-<8 位小写 hex>`，`^[0-9]{13}-[0-9a-f]{8}$` | `1792382400000-3f9a1c2d` |
| `backupId`（v1 适配） | 十进制 `backupTime` 字符串，`^[0-9]+$`；只是内存 id | `1730000000000` |
| `backupId`（v1 迁移） | `<epochMillis>-v1<8 位 hex>`，`^[0-9]{13}-v1[0-9a-f]{8}$` | `1730000000000-v1a1b2c3d4` |
| 分卷文件 | `<kind><ext>`，`ext ∈ .tar/.tar.zst/.tar.gz/.tar.xz/.tar.lz4` | `internal_data.tar.zst` |
| 分卷名约束 | basename；唯一；不得含 `/`、`\`、`..`、NUL、换行、控制字符 | — |
| `restoreId` | `<backupId>-<8 位小写 hex>` | `1792382400000-3f9a1c2d-9f3a1c2d` |
| `.bak` 目录 | `<target 父目录>/.toolkit-bak-<restoreId>-<kind>`；同 fs 的隐藏兄弟目录；冲突时追加 `-2` | `.toolkit-bak-…-internal_data` |

`backupId` 为什么用 13 位毫秒：与 v1 的 `System.currentTimeMillis()` 主键习惯一致（O：`03` §2、`04` §3），
且在当前年代是定宽，字典序≈时间序；随机后缀避免同毫秒覆盖（v1 的已知缺陷，`03` §6）。

### 2.3 与 v1 布局共存

| 路径 | v1 | v2 |
|---|---|---|
| `<home>/AppBackup/<pkg>/!BackupInfo!<pkg>.json` | 读写 | **只读**（适配器） |
| `<home>/AppBackup/<pkg>/<ts>-<part>.tar.*` | 读写 | **只读**（适配器） |
| `<home>/<pkg>-<ts>-<part>.tar.*`（v1.1.0 前扁平布局） | 旧版 | **只读**（适配器） |
| `<home>/config.json` | 读写 | 不写；仅适配器读取版本 |
| `<home>/apps/<pkg>/…` | 忽略 | 读写 |
| `<home>/toolkit.json` | 忽略 | 读写 |
| `<home>/!app!.apk` | 读写 | 不碰；v2 自身备份独立放 `self/`（09-U8 已拍板） |

约束：

1. v2 **不**写 `!BackupInfo!`、**不**改 `config.json`、**不**移动 v1 分卷；v1 也不会扫描 `apps/`。
2. 同一 `<home>` 可以同时存在 v1 与 v2 备份；UI 合并展示，但恢复走同一流水线（`10`）。
3. v2 迁移 v1 后**不自动删除** v1 文件；删除是显式动作，且必须在迁移校验通过之后（§5.6）。

## 3. 清单 schema

机器可读草案见 `docs/rea/assets/format-v2.schema.json`（JSON Schema 2020-12）。本节是它的中文解释；
两者不一致时以本节为准，并同步修 schema。

### 3.1 根元数据 `toolkit.json`

```json
{
  "schema": 2,
  "createdAt": "2026-10-19T04:00:00.000Z",
  "updatedAt": "2026-10-19T04:03:21.123Z",
  "tool": { "name": "BackupToolkit", "version": "2.0.0", "versionCode": 2000 },
  "backupHomeId": "0f7c2f5e-6a1b-4c2d-9e3f-1a2b3c4d5e6f",
  "features": { "encryption": false, "splitVolumes": false, "externalMedia": false },
  "selfBackup": {
    "file": "self/BackupToolkit-2000.apk",
    "versionName": "2.0.0",
    "versionCode": 2000,
    "sha256": "9f86d081884c7d659a2feaa0c55ad015a3bf4f1b2b0b822cd15d6c15b0f00a08",
    "createdAt": "2026-10-19T04:03:21.123Z"
  }
}
```

| 字段 | 必填 | 类型 | 语义 |
|---|---|---|---|
| `schema` | 是 | int | 固定 `2` |
| `createdAt` / `updatedAt` | 是 | string | UTC RFC 3339，毫秒可选 |
| `tool` | 是 | object | `{name, version, versionCode}`；写入者版本 |
| `backupHomeId` | 否 | string(UUID) | 根标识；复制/移动根目录后仍相同，用于诊断「同一根被挂载两次」 |
| `features` | 否 | object | 能力协商；未知键忽略。`encryption`/`splitVolumes`/`externalMedia` 目前均为 `false` |
| `selfBackup` | 否 | object | `{file, versionName, versionCode, sha256, createdAt}`；当前版本自身备份；写新成功后更新并删除旧 v2 self |

> 设计决策：不把 v1 `config.json` 的 `{versionName, versionCode}` 直接复用为 v2 根元数据，避免 v1 误判
> 「这是本工具写的根」而触发它自己的迁移逻辑（O：`04` §2）。是否额外写一个兼容 `config.json` 见 U1。

#### 3.2.2 顶层字段

| 字段 | 必填 | 类型 | 语义 / 来源 |
|---|---|---|---|
| `schema` | 是 | int | 固定 `2`；`1` 由 v1 适配器在内存中合成，不落盘 |
| `backupId` | 是 | string | 见 §2.2；创建后不可变 |
| `status` | 是 | enum | `in_progress` / `complete` / `partial` / `failed`，见 §3.2.5 |
| `createdAt` | 是 | string | 任务开始时间（UTC） |
| `finishedAt` | 条件 | string\|null | `complete`/`partial`/`failed` 时必须有；`in_progress` 时为 `null` |
| `tool` | 是 | object | `{name, version, versionCode}`；与 `toolkit.json` 的写入者可不同（升级后写新备份） |
| `device` | 否 | object | 仅诊断：`{sdk, abi, manufacturer, model, buildFingerprint}`；不含账号/序列号 |
| `package` | 是 | object | 被备份应用的快照，见 §3.2.3 |
| `selinux` | 否 | object | 见 §3.2.4；无 SELinux/未知时为 `null` |
| `requestedModes` | 否 | string[] | v1 兼容的 UI 档位：`apk`/`user`/`data`；用于列表展示 |
| `requestedKinds` | 是 | string[] | 展开后的 `kind`，见 §3.2.6；v2 恢复只认这个 |
| `skippedKinds` | 否 | object[] | `{kind, reason}`；`reason ∈ absent/not_selected/unsupported` |
| `errors` | 否 | object[] | `{kind, code, message, at}`；`status=partial/failed` 时解释失败原因 |
| `parts` | 是 | object[] | 分卷清单，见 §3.2.7；`failed` 时可为空 |
| `totals` | 否 | object | 派生缓存：`{sizeBytes, uncompressedBytes, partCount}`；不一致时以 `parts` 重算并告警 |
| `note` | 否 | string\|null | 用户备注；≤1024 字符，禁止控制字符 |
| `encryption` | 否 | object\|null | 加密元数据；未加密为 `null`。M4/v2.1：`alg/kdf/nonce/tag/chunkSize`；`sha256` 对密文，`plaintextSha256` 对明文；解密后双校验 |
| `origin` | 是 | object | `{format:"v2"}`；迁移来的 v2 清单为 `{format:"v1", layout, metadataPath, sourceKey}` |
| `compat` | 否 | object | 自由格式的兼容信息（如 v1 `backupTime2`）；v2 逻辑忽略 |

#### 3.2.3 `package` 对象

| 字段 | 必填 | 类型 | 语义 |
|---|---|---|---|
| `name` | 是 | string | 包名；Android 包名正则；禁止路径分隔符 |
| `label` | 否 | string\|null | 备份时的应用名快照（v1 `name`，O：`04` §1） |
| `versionName` | 否 | string\|null | 备份时的版本名（O：`04` §1） |
| `versionCode` | 否 | int | 备份时的版本号（O：`04` §1） |
| `userId` | 条件 | int\|null | **源**用户 id；v2 原生备份必填；v1 迁移/适配未知时为 `null`（`origin.format=v1`） |
| `userSerial` | 否 | int\|null | `UserHandle.getSerialNumberForUser()`；仅展示/诊断 |
| `appId` | 条件 | int\|null | 0–99999；Android 的 app id（uid % 100000）；v2 原生备份必填，v1 未知为 `null` |
| `uid` | 否 | int\|null | 源绝对 uid（`userId*100000+appId`）；仅诊断；恢复时按目标用户重算 |
| `signerSha256` | 否 | string\|null | **APK 签名证书 DER** 的 SHA-256，小写 hex；v1 无此字段 |
| `isSystem` | 否 | bool | 是否系统应用；仅展示 |

v2 原生备份必须写 `userId`/`appId`；`origin.format=v1` 的迁移清单允许二者为 `null`——v1 的
`!BackupInfo!` 里没有源用户/源 appId（O：`04` §1），**不要伪造**。恢复时用 `targetUserId` + 目标包解析 uid；
目标包也不存在时按 `10` §2.2 的 v1 回退探测并报 `W_UID_GUESSED`。

关于 `signerSha256`：

- 计算对象是 **签名证书 DER**（`Signature.toByteArray()`），不是整个 APK 文件；
- 小写 hex，64 字符；与 v1 门禁里的 Base64 常量可互相换算（O：`06` §3）；
- 恢复前用它做「是不是同一个 App」的校验；v1 适配时为 `null` → `W_SIGNER_UNVERIFIED`；
- 多签名/签名轮换：v2.0 只记**当前签名集的第一张证书**；完整签名历史见 U7。

#### 3.2.4 `selinux` 对象

| 字段 | 必填 | 类型 | 语义 |
|---|---|---|---|
| `dataType` | 否 | string | **类型级**上下文，去掉 MLS 类别，如 `u:object_r:app_data_file:s0`；跨用户可移植 |
| `dataContext` | 否 | string | 备份时 `/data/user/<userId>/<pkg>` 的完整上下文（含 `:c…`）；仅同用户回退用 |
| `externalDataType` | 否 | string\|null | 共享存储的类型级上下文，如 `u:object_r:media_rw_data_file:s0`；仅诊断 |

设计理由（对应 `07` §2.2 的缺陷）：

1. v1 用「父目录 `ls -Z` 的上下文，剥掉 `:c*`，整树 `chcon`」。父目录异常时会污染整棵树；
2. v2 **优先 `restorecon -RF`**（递归，由策略计算正确类型与类别），再用清单里的 `dataType` 做**校验**；v1 的
   `restorecon -F` 是非递归观测，不照抄；
3. 只有 `restorecon` 不存在/失败时才回退 `chcon`：同用户可用完整 `dataContext`；跨用户只用 `dataType`
   （类别由目标用户的策略决定，不能照搬）；
4. 回退路径必须报 `W_SELINUX_DEGRADED`；策略不支持/无法验证时默认失败并回滚（可在选项中显式放宽，见 `10` §5.4）。

#### 3.2.5 `status` 语义

| 值 | 写入时机 | 可恢复性 | UI |
|---|---|---|---|
| `in_progress` | 目录创建后、第一个 part 之前 | **禁止**（`E_BACKUP_INCOMPLETE`），除非显式「强制恢复」 | 「未完成」 |
| `complete` | 所有 `requestedKinds` 要么有 part，要么在 `skippedKinds`（`absent/unsupported`） | 允许 | 「完整」 |
| `partial` | 至少一个 part 写失败，但已有 ≥1 个可用 part | 允许，但 `allowPartial` 默认 false；每次显式确认，只恢复存在且勾选的 part（`W_PARTIAL_BACKUP`） | 「部分」 |
| `failed` | 没有可用 part | 禁止（`E_BACKUP_INCOMPLETE`） | 「失败」 |

关键细节：**「源路径不存在」不是失败**。v1 的 `backup()` 对不存在的路径直接 `echo '跳过'; return`（O：`03` §3.6），
所以「应用没有 obb / 没有 Android/data」应记为 `skippedKinds.reason=absent`，整体仍是 `complete`。

#### 3.2.6 `requestedModes` → `requestedKinds` 展开

| mode（v1 UI） | kind | 说明 |
|---|---|---|
| `apk` | `package` + `apk_obb` | v1 `apk()` = `backup_apk && backup apk_obb`（O：`03` §3.3） |
| `user` | `internal_data` + `internal_device_protected` | v1 `user()` 同时备份 `/data/user` 与 `/data/user_de`（O：`03` §3.3） |
| `data` | `external_data` | v1 `data()` = `/sdcard/Android/data/<pkg>`（O：`03` §3.3） |

v2 API 允许直接按 `kind` 选择；`requestedModes` 只用于兼容三列 UI。恢复时以 `requestedKinds`/`parts` 为准，
不根据 mode 反推。

#### 3.2.7 `parts[]` 与 `kind` 枚举

| `kind` | v1 分卷名 | 归档形状 | 源路径 | 恢复目标 |
|---|---|---|---|---|
| `package` | `apk` | **扁平**：顶层只有 `*.apk`（base + splits） | `pm path` 返回的 base/split APK 所在目录 | `pm install-*`（不落用户目录） |
| `apk_obb` | `apk_obb` | 单目录：顶层必须是 `<pkg>/` | `<sd>/Android/obb/<pkg>` | `<targetSd>/Android/obb/<pkg>` |
| `internal_data` | `user` | 单目录：`<pkg>/` | `/data/user/<userId>/<pkg>` | `/data/user/<targetUserId>/<pkg>` |
| `internal_device_protected` | `user_de` | 单目录：`<pkg>/` | `/data/user_de/<userId>/<pkg>` | `/data/user_de/<targetUserId>/<pkg>` |
| `external_data` | `data` | 单目录：`<pkg>/` | `<sd>/Android/data/<pkg>` | `<targetSd>/Android/data/<pkg>` |
| `external_media`（预留） | — | 单目录：`<pkg>/` | `<sd>/Android/media/<pkg>` | 同左 |
| `external_files`（预留） | — | 待定 | 用户选择的目录 | 需要路径映射表，v2.1 |

> v1 的 `restore` 用 `tar -xC "${path%/*}" -o`，依赖归档里带 `<pkg>/` 这一层（O：`03` §3.7）；
> `restore_apk` 则直接解到 `TMPDIR` 并 `find -maxdepth 1 -name '*.apk'`（O：`03` §3.9）。两种形状必须在
> 校验器里分开处理（`10` §7）。

| `parts[]` 字段 | 必填 | 类型 | 语义 |
|---|---|---|---|
| `kind` | 是 | enum | 上表 |
| `file` | 是 | string | 相对 `manifest.json` 的 basename；§2.2 约束 |
| `compression` | 是 | enum | `none` / `zstd` / `gzip` / `xz` / `lz4`；对应 v1 扩展名（O：`03` §3.4） |
| `level` | 条件 | int\|null | `compression=zstd` 时 1–19；其它为 `null`/省略 |
| `sizeBytes` | 是 | int | **落盘文件**字节数；未加密=压缩文件大小，加密=**密文**大小 |
| `sha256` | 是 | string | **落盘字节**的 SHA-256，小写 hex；未加密=压缩文件，加密=**密文**；v2 文件不允许 `null` |
| `entryCount` | 否 | int | tar 条目数；用于校验上限/进度 |
| `uncompressedBytes` | 否 | int | 明文 tar 解包后的字节数；用于空间预检/zip-bomb 上限；建议记录 |
| `sourcePath` | 否 | string | **deprecated**：v2.0 写入器**禁止生成**；读取兼容/调试用；诊断只写脱敏逻辑路径；恢复时禁止用它决定写哪里 |
| `excludes` | 否 | string[] | 声明式排除项（相对 `<pkg>/`），如 `["lib","cache"]` |
| `seq` | 否 | int | 预留：分卷序号（v2.1 的大备份分卷） |
| `plaintextSha256` | 否 | string\|null | 加密时**明文**的 SHA-256；未加密为 `null`；解密后与 `sha256`（密文）同时校验 |

`parts[].file` 必须与 `kind` 前缀一致（`package.*`、`internal_data.*`…），且同一备份内唯一。读取器**只信
`file`**，不根据扩展名猜格式；扩展名只用于人类可读性和 v1 兼容。

> **保留 kind 的处理**：`external_media`/`external_files` 目前只有枚举，没有归档形状/恢复目标定义。
> 备份端遇到它们应记 `skippedKinds.reason=unsupported`；恢复端若用户只选了这些 kind，报 `E_FORMAT_UNKNOWN`；
> 不得用猜测的路径实现。v2.1 定义后再补 `10` §7.2 的形状表。

> **加密字段（09-U6 / 10-U7 已拍板）**：加密是 M4/v2.1 功能，`schema` 仍为 2。`encryption` 记录
> `alg`/`kdf`/`nonce`/`tag`/`chunkSize`；`parts[].sha256` 对**落盘密文**，`plaintextSha256` 对**明文**；
> `sizeBytes` 为密文大小，`uncompressedBytes` 为明文 tar 大小；解密后必须同时校验两个哈希。
> 未加密时 `encryption=null`、`plaintextSha256=null`。

> **sourcePath（09-U5 已拍板）**：v2.0 写入器**禁止**生成绝对 `parts[].sourcePath`；字段仅保留读取兼容/调试，
> 在 schema 中标 `deprecated`。诊断包只写脱敏后的逻辑路径（如 `/data/user/<userId>/<pkg>`），不写真实绝对路径。

### 3.3 应用级 `index.json`（派生缓存）

```json
{
  "schema": 2,
  "pkg": "com.example.app",
  "generatedAt": "2026-10-19T04:03:22.000Z",
  "source": "scan",
  "backups": [
    {
      "backupId": "1792382400000-3f9a1c2d",
      "status": "complete",
      "createdAt": "2026-10-19T04:00:00.000Z",
      "finishedAt": "2026-10-19T04:03:21.123Z",
      "label": "示例应用",
      "versionName": "8.0.40",
      "versionCode": 2400,
      "sizeBytes": 172904923,
      "note": "登录前状态",
      "parts": ["package", "internal_data", "external_data"],
      "icon": true
    }
  ]
}
```

规则：

1. `index.json` **永远可由** `apps/<pkg>/*/manifest.json` 重建；
2. 读取时若 `index.json` 缺失、`schema` 不符、`generatedAt` 早于最新的 `manifest.json` mtime，或 `pkg` 不符，
   则扫描重建，并报 `W_INDEX_STALE`；
3. 恢复/删除/校验**不得**以 `index.json` 为真值；删除单个备份后也要以 `manifest.json` 是否存在为准；
4. `icon` 只是「`icon.png` 是否存在」的缓存；不参与恢复。

### 3.4 取值与规范化

| 项 | 规则 |
|---|---|
| 时间 | UTC RFC 3339；写入带毫秒 + `Z`；读取接受任意偏移并归一化为 UTC |
| 哈希 | 小写 hex；比较时大小写不敏感；长度必须 64 |
| 整数 | int64；`versionCode` 允许超过 32 位（Android 已支持 long） |
| 包名 | `^[A-Za-z][A-Za-z0-9_]*(\.[A-Za-z][A-Za-z0-9_]*)+$`；拒绝 `/`、`\`、`..`、空段 |
| `label` | ≤256 字符；禁止控制字符（`\u0000-\u001f`、`\u007f`） |
| `note` | ≤1024 字符；禁止控制字符；允许换行？**不允许**，用空格替代，避免 UI/日志注入 |
| JSON 编码 | UTF-8，无 BOM；写入 2 空格缩进 + 末尾换行（便于 diff）；读取不依赖格式 |
| 未知字段 | 读取忽略；**更新清单时保留**（实现应保存原始 map，避免升级丢字段） |

### 3.5 schema 校验顺序

读取 `manifest.json` 时按以下顺序失败（错误码见 `10` §8）：

1. 文件存在、可读、JSON 合法 → 否则 `E_MANIFEST_INVALID`；
2. `schema` 是整数且 `≤2`；`1` 走适配器；`>2` → `E_SCHEMA_UNSUPPORTED`；
3. 必填字段齐全、类型正确、枚举合法 → 否则 `E_MANIFEST_INVALID`；
4. `status` 可恢复（`in_progress`/`failed` → `E_BACKUP_INCOMPLETE`）；
5. `parts[].file` 是 basename 且唯一 → 否则 `E_MANIFEST_INVALID`；
6. 每个 part 的文件存在、`sizeBytes` 匹配、`sha256` 匹配 → 否则 `E_PART_MISSING`/`E_PART_SIZE_MISMATCH`/`E_PART_HASH_MISMATCH`；
7. `totals` 与 `parts` 不一致 → `W_TOTALS_MISMATCH`，以 `parts` 为准重算。

## 4. 备份写入协议（原子性）

### 4.1 任务序列

```
1. 生成 backupId；创建 <home>/apps/<pkg>/<backupId>/
2. 写 manifest.json（status=in_progress, parts=[], requestedModes/requestedKinds,
   origin={format:"v2"}, createdAt, finishedAt=null）
3. 按固定顺序处理 requestedKinds：
      package → apk_obb → internal_data → internal_device_protected → external_data
   对每个 kind：
      a. 源路径不存在 → skippedKinds += {kind, absent}；继续
      b. 写 <kind><ext>.tmp；同步；rename 为 <kind><ext>
      c. 计算 sizeBytes/sha256（见 4.2）
      d. 原子更新 manifest（追加 part）
      e. 失败 → errors += {kind, code, at}；若已有 part 则 status=partial，否则 status=failed；
         停止后续 kind（fail-fast）
4. 写 totals、finishedAt、最终 status；原子更新 manifest
5. 重建/更新 <pkg>/index.json（best effort）
```

固定顺序的理由：`package` 先写，恢复时可以先安装 APK 再恢复数据；`internal_*` 在 `external_data` 之前，
让内部数据（更关键）优先占用空间/时间。恢复的提交顺序按「较不重要/可重建 → 最重要」排列
（`apk_obb` → `external_data` → `internal_device_protected` → `internal_data`，见 `10` §5.3），
不是备份顺序的简单倒序；两者目的不同：备份是「先保住最重要的」，恢复是「失败时尽量少回滚」。

### 4.2 分卷写入与哈希

- 写入先落到同目录的 `<file>.tmp`，完成后 `rename`；避免半截文件被当成 part。
- 压缩仍沿用 v1 的「一个 zstd 出四种格式」设计（O：`03` §3.4）：`none` 用 `tar -f`，其它用
  `tar ... | zstd -<level> --format=<fmt> -fo`。
- `sha256` 在文件写完后**再读一遍**计算（v2.0 不要求边写边算；实现可用 `sha256sum` applet 或 Java
  `MessageDigest` 流式读）。理由：busybox 精简版没有 `tee`/进程替换，边写边算会引入脆弱管道；
  多一次顺序读的代价可接受。
- 写完后 `fsync` 文件与父目录（`sync` 或 Java `FileDescriptor.sync()`），再原子更新清单。
- 清单本身用 `manifest.json.tmp` + `rename`；`fsync` 后再更新 `index.json`。

### 4.3 中断/崩溃后的识别

| 现场 | 判定 | 处理 |
|---|---|---|
| `manifest.status=in_progress` 且 `manifest.json` mtime 超过阈值（如 10 分钟） | 备份未完成 | UI 显示「未完成」；恢复拒绝（`E_BACKUP_INCOMPLETE`）；提供删除 |
| 目录里有 `.tar*` 但清单未列出 | 崩溃在「rename 分卷」与「更新清单」之间 | 报 `W_ORPHAN_PARTS`；**不自动补录**（可能是半截/旧文件）；提供删除或人工检查 |
| `manifest.status=partial/failed` | 明确记录的失败 | 按 `10` 的可恢复性处理 |
| 目录里没有 `manifest.json` 但有分卷 | 不是 v2 备份 | 忽略；`W_ORPHAN_PARTS`；不自动迁移 |

### 4.4 空间预检

预检在写第一个 part 之前做；不足则 `E_SPACE`，不产生任何文件。

**备份侧**

```
need = Σ estimatedSourceBytes(kind) × ratio(compression) + 64 MiB
ratio(none)=1.0；ratio(zstd/gzip/xz/lz4)=1.0（预检不假设压缩收益；实际写盘通常更小）
available = df -Pk <home> 的可用字节
要求 available - need ≥ max(256 MiB, available×5%)
```

`estimatedSourceBytes` 用 `du -sk`（busybox）或 `find` 汇总；对 `package` 用 APK 文件大小之和。

**恢复侧**（与 `10` §2.2 共用）

```
newBytes  = Σ (part.uncompressedBytes ?? part.sizeBytes × 3)
oldBytes  = 目标目录当前大小（du -sk；不存在=0）
need      = newBytes + oldBytes + 64 MiB
```

`oldBytes` 必须计入：Commit 期间 `.bak` 与新数据**同时存在**（rename 不复制，但旧数据仍占空间），
峰值 = 新 + 旧。内部分区与共享存储分区分别检查。若实际解压超过预估（尤其 v1 无 `uncompressedBytes`
时用 `size×3` 估算），写盘失败按 `E_SPACE` 中止并清理 staging；目标不受影响。

### 4.5 锁与并发

- 写任务启动时创建 `<home>/.toolkit/lock`（内容：`taskId`、pid、startedAt）；已存在且未过期 → `E_BUSY`。
- 任务正常/异常退出都删除锁；崩溃遗留的锁按「pid 不存在或超过 24h」视为过期。
- 备份与恢复共用一把锁（同一时刻只允许一个重 IO 任务）。

## 5. v1 → v2 只读适配器

### 5.1 目标

让 v1 备份**无需迁移**就能走 v2 的恢复流水线（`10`），同时把 v1 的已知缺陷显式建模为告警/错误，而不是
在适配层「猜着修好」。

### 5.2 发现与分组算法

输入：`<home>`、`<pkg>`。输出：`List<BackupSet>`（按 `sortTime` 降序）。

```
scan(pkg):
  result = {}
  appDir = <home>/AppBackup/<pkg>

  # A. v1.1.0+ 目录布局
  if appDir exists:
    meta = parse(!BackupInfo!<pkg>.json)        # 容忍缺失字段；解析失败 → 空
    files = list(appDir) matching:
      ^([0-9]+)-(apk|apk_obb|user|user_de|data|obb)\.tar(\.(zst|gz|xz|lz4))?$
    groups = groupBy(ts, files)
    for entry in meta.backupList:
      ts = entry.backupTime
      result[ts] = fromMeta(entry, groups[ts], layout="appdir")
    for ts in groups not in meta:
      result[ts] = fromFiles(ts, groups[ts], layout="appdir", orphan=true)

  # B. v1.1.0 之前的扁平布局
  flat = list(<home>) matching:
    ^<pkg>-([0-9]+)-(apk|apk_obb|user|user_de|data|obb)\.tar(\.(zst|gz|xz|lz4))?$
  for ts in groupByTs(flat):
    if ts not in result: result[ts] = fromFiles(ts, ..., layout="flat")
    else: 记录 W_ORPHAN_PARTS（同 ts 的扁平文件被目录布局覆盖）

  return sortDesc(result, key = sortTime)
```

`sortTime = backupTime2 != 0 ? backupTime2 : backupTime`（O：`04` §1）。适配器把它暴露为
`BackupSet.sortTime`，但不写进 v2 清单（迁移时存 `compat.v1.backupTime2`）。

### 5.3 字段映射

| v1 | v2 | 规则 |
|---|---|---|
| `!BackupInfo!<pkg>.json` → `pkg` | `package.name` | 必填；与目录名不一致时以 JSON 为准并告警 |
| `backupList[].name` | `package.label` | 缺失/空 → `null` |
| `backupList[].versionName` | `package.versionName` | 缺失 → `null` |
| `backupList[].versionCode` | `package.versionCode` | 缺失 → `0`（`NotWriteDefaultValue` 会省略 0，O：`04` 开头） |
| `backupList[].backupTime` | `backupId`（内存）、`createdAt` | `backupId=String(ts)`；`createdAt=Instant.ofEpochMilli(ts)` |
| `backupList[].backupTime2` | `compat.v1.backupTime2` + `sortTime` | 仅排序/迁移保留 |
| `backupList[].note` | `note` | 缺失 → `null` |
| `config.json` 的 `versionName/versionCode` | `tool`（根级视图） | 只读；用于显示「哪个版本写的」 |
| — | `package.userId` | **未知** → `null`；`compat.v1.userIdUnknown=true`。v1 JSON 不含源用户，**不推断为当前用户** |
| — | `package.appId` / `uid` | **未知** → `null`；恢复时回退探测（`W_UID_GUESSED`） |
| — | `package.signerSha256` | **未知** → `null`（`W_SIGNER_UNVERIFIED`） |
| — | `selinux` | **未知** → `null` |
| — | `status` | 有 ≥1 个可用 part 且文件齐全 → `complete`；有 ≥1 个可用 part 但缺文件 → `partial`；没有任何可用 part（无 JSON/无分卷）→ `failed`（不可恢复） |
| — | `requestedKinds` | 由实际存在的 part 反推（见 5.4） |
| — | `requestedModes` | 由 kinds 反推：含 package/apk_obb → `apk`；含 internal_* → `user`；含 external_data → `data` |
| — | `origin` | `{format:"v1", layout:"appdir"\|"flat", metadataPath, sourceKey}`；`sourceKey` 用相对 `<home>` 的路径；`metadataPath` 绝对路径仅诊断/导出脱敏 |
| — | `parts[].sha256` | **适配器内存对象**未知 → `null`（v1 无校验，O：`07` §3.1）→ `W_HASH_UNVERIFIED`；一旦 `migrate` 落盘必须重新哈希，schema 要求非 `null` |
| — | `parts[].sizeBytes` | 文件 `stat` 结果 |
| — | `parts[].uncompressedBytes` | 未知 → `null`；恢复空间预检用 `sizeBytes×3` 保守估算 |

### 5.4 分卷映射

| v1 part | v2 `kind` | 备注 |
|---|---|---|
| `apk` | `package` | 扁平 APK 集 |
| `apk_obb` | `apk_obb` | 单目录 `<pkg>/` |
| `user` | `internal_data` | 单目录 `<pkg>/` |
| `user_de` | `internal_device_protected` | 单目录 `<pkg>/` |
| `data` | `external_data` | 单目录 `<pkg>/` |
| `obb`（v1.1.0 前） | `apk_obb` | 迁移时把文件名重写为 `apk_obb.*`（O：`04` §3） |

`requestedKinds` 反推规则：按上表把存在的 part 映射为 kind；不推断「用户当时选了什么 mode」，
只反映「磁盘上实际有什么」。这与 v1 恢复时用 glob 登记 `*_CP` 的行为一致（O：`03` §3.10）。

### 5.5 v1 缺陷在适配层的显式建模

| v1 事实（O） | 适配层处理 | 恢复时后果 |
|---|---|---|
| 无 uid/SELinux/signer/哈希（`03` §6、`07` §2.1/2.2/3.1） | 字段置 `null`，不伪造 | `W_HASH_UNVERIFIED`、`W_SIGNER_UNVERIFIED`、`W_UID_GUESSED`；归档校验仍然强制执行 |
| `user`/`data` 命名反直觉（`03` §1） | 按分卷名映射，不按用户直觉 | 无 |
| `user` 模式同时产生 `user` + `user_de`（`03` §3.3） | 两个独立 kind | 恢复时可分开选择 |
| 分卷名用 `<ts>-<part>`，无清单记录格式（`04` §3） | 扩展名 → `compression`；未知扩展名 → `E_FORMAT_UNKNOWN` | 不改名就能恢复；改名后仍能按清单（迁移后）恢复 |
| `backupTime` 同毫秒冲突（`03` §6） | 适配器按 `backupTime` 分组；同 ts 多组视为同一备份 | 无法区分；UI 提示 `W_BACKUP_TIME_COLLISION`（m6 已登记） |
| `get_app_uid` 用 `$_USER_ID$appid` 字符串拼接（`03` §3.10） | 适配器不复制该逻辑；v2 用算术 | `appId < 10000` 且 `userId > 0` 时 v1 会算错 uid（普通应用 appId 通常 5 位，碰巧正确）；v2 修正（I9） |
| 无 `media` 支持（`03` §3.10 注释） | 不合成 `external_media` | 无 |
| `lib` 被排除、恢复时重建软链（`03` §3.8） | 适配器保留 `excludes` 提示 | v2 用 `nativeLibraryDir` 重建（`10` §5.5） |
| v1 `config.json` 不存在时视为「外来目录」（`04` §2） | 适配器不依赖它 | v2 根有 `toolkit.json`，不写 `config.json` |

### 5.6 迁移（显式、幂等）

两种动作，UI 必须区分：

| 动作 | 行为 | 写盘 | 用途 |
|---|---|---|---|
| `reindex` | 只扫描 v1，生成内存 `BackupSet`/UI 索引 | 不写 v1；可选写 v2 `index.json` 缓存 | 日常浏览/恢复，零风险 |
| `migrate` | 把选中的 v1 备份复制成 v2 目录 | 只写 v2；v1 原样保留 | 用户想统一格式/加哈希/后续增量 |

`migrate` 步骤：

```
1. 预检：源文件存在、空间足够（Σ sizeBytes + 64 MiB）、目标目录不冲突
2. sourceKey = "v1:" + layout + ":" + 相对 <home> 的路径 + "#" + ts
   例：v1:appdir:AppBackup/<pkg>/!BackupInfo!<pkg>.json#<ts>；不再用绝对 metadataPath
3. newBackupId = <ts>-v1<sha256(sourceKey)[0:8]>
4. 若 <pkg>/<newBackupId>/manifest.json 已存在且 origin.sourceKey == sourceKey → 跳过（幂等）
5. 创建目录；逐个复制（同文件系统优先 hardlink，失败/跨 fs 则 copy）
6. 复制后重新计算 sizeBytes/sha256（不信任源）
7. 写 manifest（status=complete/partial；requestedKinds/requestedModes 按 5.4 反推；
   package.userId/appId=null；origin={format:"v1",layout,metadataPath,sourceKey}；
   compat.v1={backupTime2}）；写 index.json
8. 失败：删除未完成的 v2 目录（或标记 failed），不动 v1
9. 成功：v1 保留；UI 标记「已迁移」；删除 v1 是单独的用户动作，且需再次确认
```

幂等：`sourceKey` + `newBackupId` 双重判定；重复执行 `migrate` 不会产生第二份。
`hardlink` 注意：FAT/exFAT（多数 SD 卡）不支持；必须捕获失败并回退到 copy，不能假定成功。
即使 hardlink 成功，也不要把「共享 inode」当成不可变保证：v1 文件被原地修改会让 v2 的 `sha256` 失配
（恢复预检报 `E_PART_HASH_MISMATCH`），这正是保留哈希的意义。
迁移后的 v2 清单仍带 `origin.format=v1`，恢复时可按需显示 `W_LEGACY_FORMAT`（但哈希/签名已可校验）。
`origin.metadataPath` 可保留绝对路径作诊断，但导出时脱敏；幂等键只用相对 `<home>` 的 `sourceKey`。
v1 的 `!app!.apk` **不迁移**；v2 self 独立放 `self/`（09-U8 已拍板）。

### 5.7 适配器的只读契约

- `BackupSet.readOnly = true`；任何「改备注/删备份/覆盖」动作在 v1 视图上禁用，或引导先 `migrate`；
- 适配器不得创建/删除/重命名 v1 目录内的任何文件；
- 适配器不得把 v1 的相对路径写进 v2 `manifest.json` 的 `file` 字段（迁移时复制并重新命名）；
- UI 可以缓存 `BackupSet`，但每次恢复前必须重新扫描（用户可能在外部改了文件）。

## 6. 版本演进与兼容规则

| 变更 | 是否升 `schema` | 读取方行为 |
|---|---|---|
| 新增可选字段 | 否 | 忽略未知字段；更新时保留 |
| 新增 `kind` | 否 | 旧实现跳过未知 kind（`W_UNKNOWN_PART_KIND`）；若用户只选了未知 kind → `E_FORMAT_UNKNOWN` |
| 新增 `compression` 值 | 否 | 旧实现无法解压 → `E_FORMAT_UNKNOWN`（不要猜） |
| 字段改名/删除/类型变化 | **是**（→3） | 旧实现 `E_SCHEMA_UNSUPPORTED` |
| `status` 新增枚举值 | **是** | 旧实现 fail-closed，避免误判「可恢复」 |
| 分卷拆卷（`seq`） | 否（预留） | 旧实现只认 `seq` 缺失/0；有 `seq` 时 `E_FORMAT_UNKNOWN` |

写入方规则：

1. 只写 `schema:2`；
2. 保留未知字段（读取时保存原始 JSON map，更新时合并）；
3. 不因为「当前实现不认识」而删除旧字段；
4. 每次 schema 变更同步更新本文、`10` 的错误码表、`assets/format-v2.schema.json`。

## 7. 与 `08` 的差异 / 修订记录

| 08 原文 | 本文修订 | 原因 |
|---|---|---|
| `apps/<pkg>/manifest.json` 叫「索引（唯一真值）」 | 改名 `index.json`，明确是**派生缓存**；单次备份的 `manifest.json` 才是真值 | 两个同名文件容易混淆；索引可重建 |
| `kind ∈ {package, apk_obb, internal_data, external_data, external_obb, media}` | `package, apk_obb, internal_data, internal_device_protected, external_data` + 预留 `external_media, external_files` | 08 漏了 v1 的 `user_de`；`apk_obb`/`external_obb` 重复 |
| 清单字段 `uid/userSerial/selinuxContext` | 拆成 `package.userId/appId/uid/signerSha256` + `selinux{dataType,dataContext}` | 多用户要区分源/目标 uid；SELinux 跨用户不能照搬类别 |
| `parts[]` 只有 `{kind,file,format,level,sizeBytes,sha256,entryCount}` | 增加 `compression`、`uncompressedBytes`、`excludes`、`seq`；`sourcePath` 先加后 deprecated（09-U5） | 空间预检、归档形状校验、分卷演进 |
| 兼容映射只写 `user→internal_data`、`data→external_data` | 补 `apk→package`、`apk_obb→apk_obb`、`user_de→internal_device_protected`、`obb→apk_obb` | 覆盖 v1 全部 5 种分卷 |
| 迁移「先写清单」 | 拆成 `reindex` / `migrate`；`migrate` 复制并重新哈希，`sourceKey` 幂等 | v1 分卷可能被外部改过；不能只写清单就信任 |
| 未定义 `status`/`requested*`/`errors` | 增加完整状态机与字段 | 中断/部分备份必须可识别 |
| 未定义写入原子性/空间峰值 | §4 增加 tmp+rename、哈希、锁、`new+old` 峰值 | 对应 v1 的半截文件/无空间预检 |
