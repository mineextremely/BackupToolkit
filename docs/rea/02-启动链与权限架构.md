# 02 · 启动链与权限架构

这是整个 App 最关键、也最值得在重构时照抄的设计：**它不自带提权，只借用设备已有的 root；用「一个常驻 root 进程 + 一个常驻 root shell」把危险能力集中起来，UI 进程退化为纯客户端。**

---

## 1. 进程拓扑

```
┌──────────────────────────────┐        ┌─────────────────────────────────────┐
│ 进程 A：UI 主进程             │        │ 进程 B：root 守护进程（可选常驻）    │
│ 包名/uid = <app uid>          │        │ uid = 0，无 APK 身份                 │
│ MyApplication → p009else.…    │ bind   │ app_process64 -Xnoimage-dex2oat …    │
│ SplashActivity / MainActivity │───────►│   --nice-name=<pkg>:root:daemon      │
│ 16 个自有类 + 库               │ AIDL   │ CLASSPATH=<DEX-cache>/main.jar       │
│                               │        │ 入口 com.topjohnwu.superuser.        │
│  ① IRootManager（包/用户 API） │        │      internal.RootServerMain         │
│  ② IBackupManager（备份目录）  │        │  └─ 反射实例化 p004class.Cwhile       │
│  ③ IFileSystemService（文件IO）│        │     （libsu RootService 子类）        │
└──────────────────────────────┘        └─────────────────────────────────────┘
        │                                          │
        │ ② Shell（Runtime.exec("su","--mount-master")）
        ▼                                          ▼
┌──────────────────────────────────────────────────────────────────────────────┐
│ 进程 C：root shell（su 拉起的 sh，长生命周期，App 存活期间复用）               │
│ 启动时被 source 了 res/raw/root_shrc.sh → 之后所有备份/恢复都在这里跑           │
│ PATH=<filesDir>/bin:$PATH  HOME=<filesDir>/home                             │
└──────────────────────────────────────────────────────────────────────────────┘

┌──────────────────────────────┐
│ 进程 D：":crash" 独立进程      │  CrashActivity 专用（application 初始化被跳过）
└──────────────────────────────┘
```

设计含义：

| 通道 | 承担职责 | 为什么必须分出来 |
|---|---|---|
| **root 守护进程（AIDL）** | 以 uid=0 调 `IPackageManager`（跨用户枚举包/改 enable 状态/取启动 Intent）、读写任意路径文件、扫描/迁移备份目录 | UI 进程只有 `INTERACT_ACROSS_USERS` 一个权限；`/data/user*`、`/sdcard/Android/data/<其他包>` 用普通权限根本读不到 |
| **root shell（su + sh）** | 真正的批量作业：tar/zstd、`pm install-*`、`am force-stop`、`killall`、`chown`、`restorecon` | 用 shell 拼命令比写 binder 接口迭代快；能复用 busybox/zstd 二进制 |
| **普通 App 进程** | 全部 UI、JSON 解析、列表、偏好 | 一旦被 kill，备份作业不受影响（作业在 root shell 里已经 `exec` 出去） |

## 2. 壳 Application 技巧

`r2ixzp.toolkit.MyApplication` 本身几乎是空的：

```java
public final void attachBaseContext(Context context) {
    super.attachBaseContext(context);
    if (ActivityThread.currentProcessName().endsWith(":crash")) return;   // 崩溃进程不复用真 Application
    Instrumentation.newApplication(p009else.Cimport.class, context).onCreate();
}
```

作用：**同一份 APK 在两个进程里跑两套 Application 初始化**。`:crash` 进程不初始化 libsu/日志/偏好，避免崩溃上报路径自我递归。

真正的 `Application` 是 `p009else.Cimport`，它做 6 件事：

1. `getExternalFilesDir("log")` → **`/sdcard/Android/data/<pkg>/files/log/error.log`**（自己拼路径，不用系统 API，因为要保证 root 侧 shell 也能写同一路径）；
2. 注册 `Thread.setDefaultUncaughtExceptionHandler`（写 error.log → 起 `:crash` 进程 Activity）；
3. 取 `SharedPreferences`（`<pkg>` 与 `settings` 两个文件）；
4. `Process.myUserHandle()` → 记录当前用户 id（多用户运行时的基准）；
5. 预置 libsu 全局 `Shell.Builder`：**flags=10（`--mount-master` + verbose Log）、timeout=11s**；
6. 建立 `Messenger`（`Cthrow.f657default`）用于「后台线程 → 主线程 Toast」的跨线程提示。

> `--mount-master` 很关键：`su --mount-master` 让 shell 处于 **global mount namespace**，否则读不到其他用户 / 其他挂载点（如 rclone 挂载的云盘、`/mnt/media_rw/*`）下的备份目录。

## 3. 启动时序（真实调用链）

```
[App 冷启动]
SplashActivity.onCreate
  └─ 首次运行弹「数据备份需要 Root，请确认本 App 未被恶意修改」（sharedPref show_app_description）
  └─ run()（后台线程）
       ├─ 若 root 服务尚未连接：
       │    RootService.start(Intent → p004class.Cwhile, conn)
       │      └─ libsu 生成 shell 脚本：
       │         ( CLASSPATH=<deviceProtected cache>/main.jar \
       │           /system/bin/app_process64 -Xnoimage-dex2oat \
       │           --nice-name=<pkg>:root:daemon \
       │           /system/bin <pkg>:root:daemon \
       │           com.topjohnwu.superuser.internal.RootServerMain 'p004class.Cwhile' <uid> daemon \
       │           >/dev/null 2>&1 ) &
       │      └─ root 侧 RootServerMain 反射 new p004class.Cwhile() → onBind 返回 IRootManager
       └─ 若已连接：见下

RootService 连接回调 p012final.Creturn.onServiceConnected(binder)
  ├─ p009else.Cimport.m920extends(binder)：
  │     IRootManager  = binder.asInterface("r2ixzp.toolkit.aidl.IRootManager")
  │     IBackupManager = IRootManager.getBackupManager()      // binder.asInterface("…IBackupManager")
  │     IFileSystem    = IRootManager.getFileSystemService()  // libsu IFileSystemService
  │     rootManager.registerMessenger(messenger)              // 双向：root 侧也能发 Toast
  ├─ Service.Cthrow.m124volatile(ctx)   // ① 部署二进制
  │     getprop ro.product.cpu.abilist → 从高到低挑 ABI
  │     assets/bin/<abi>.zip → 解到 <filesDir>/bin/（busybox / toolkit / zstd）
  │     File.setExecutable(true,false) 递归 chmod +x
  │     建 <filesDir>/home；env_version=20 写入 prefs（下次跳过）
  ├─ Service.Cthrow.m122private(ctx, shell) // ② 注入环境
  │     export _ENV_DIR=<filesDir>
  │     export PATH=$_ENV_DIR/bin:$PATH HOME=$_ENV_DIR/home
  │     cd $HOME
  ├─ Service.Cthrow.m118abstract(shell)     // ③ source shell 引擎
  │     openRawResource(R.raw.root_shrc) → 逐行喂给同一个 root shell
  │     脚本末尾 echo '0' 作为「加载成功」信号（输出 != "0" 即报「环境错误」）
  └─ startActivity(MainActivity)
```

失败分支都有明确文案：`root_service_start_failure`（Root服务启动失败）/ `env_error`（环境错误）/ `no_root_permission`（没有root权限？！！）。

## 4. libsu 的使用方式（混淆后位置 → 原始职责）

| 混淆位置 | libsu 原始类 | 关键行为 |
|---|---|---|
| `Activity.Cthrow` | `com.topjohnwu.superuser.ipc.RootService` | `start()/stop()/bind()` 静态入口；`DAEMON_MODE` = `com.topjohnwu.superuser.DAEMON_MODE`；daemon 通道用 `ServiceManager.getService("libsu-<pkg>")` |
| `Intent.Cnew` | RootService 客户端管理（`RootIPC`/daemon 管理） | 把 `assets/main.jar` 写到 **device-protected cache**，拼 `app_process` 命令行，`--nice-name=<pkg>:root:daemon` |
| `Intent.Cimport` | `Shell.Builder` | 默认 timeout 20s；**开 shell 优先用 `su --mount-master`，退化 `su`，再退化 `sh`** |
| `Intent.b` / `Cvolatile` / `Cthis` | `Shell` 实例 / 全局单例容器 | 单例 root shell（`p011false.Cpublic.m922default()`），同进程内只允许建一个 root shell |
| `Intent.Cstrictfp` | `Shell.Job` | `add(...)` 加命令 → `exec()` 返回 `Result`，`Result.code` 即退出码 |
| `Intent.Cinterface` / `Cimplements` / `Cpublic` | `FileSystemService` / `ExtendedFile` | 走 binder 的 `File` 替代品：`newInputStream()/newOutputStream()/list()/exists()/mkdirs()/delete()/getCanonicalPath()` |
| `File.Cthrow` / `File.Cwhile` | libsu 的 `File`/`Stream` 抽象 | 上述 API 的底层实现 |
| `p004class.Cwhile` | **本项目自己的** `RootService` 子类 | `onBind` = 返回 `p004class.Cnative`（IRootManager 实现） |
| `p005const.Cthrow` | 本项目 Service 基类 | 重写 `getExternalFilesDir()` 为 `/sdcard/Android/data/<pkg>/files/<x>`（root 进程里没有真实 Context）；内含 XOR 解密器 |

`Shell` 的命令执行形态（`Service.Cthrow.m123strictfp()` → `new Cstrictfp(shell)` → `add(cmd)` → `exec()`）：

```java
Shell.Job job = new Shell.Job(mainRootShell);
job.add("app_backup com.tencent.mm 1730000000000 'apk&&user&&data'");
int code = job.exec().code;     // 0 = 成功
```

所以 Java 侧所有「重活」都退化成 **一行字符串命令 + 退出码判定**，输出/错误信息通过 `p011false.Cwhile` 回调逐行收集进日志。

### 5.3 `IFileSystemService`（libsu）

UI 进程内的**所有**文件操作（读 `!BackupInfo!*.json`、写图标 PNG、`list()` 备份目录、`exists()` 判断）都走这个 binder，因此：

- 不需要任何存储权限；
- 能读写 `/data/user*/<uid>/<pkg>`、`/sdcard/Android/data/<别人包名>`；
- 代价是**每次 list/read 都是 IPC**，列表页刷新有一定开销（`AppBackupRestoreActivity` 里靠缓存 `HashMap` + 后台线程缓解）。

## 6. 为什么 `root_shrc.sh` 要 source 到 shell 而不是每次执行

- libsu 的 root shell 是**常驻进程**，`sh` 读 `stdin` 逐条执行并回显标记，变量/函数/别名都可跨命令保留；
- 于是 335 行脚本只在启动时执行一次，之后 Java 侧只需发 `app_backup <pkg> <ts> '<modes>'` 这样的**一行**；
- 别名（`alias tar='busybox tar'`、`alias zstd='zstd -T0 -qr --ultra --priority=rt'`）依赖的是同一个 shell 会话，**改成「每条命令独立 sh -c」就必须显式展开**——这是重构时最容易踩到的坑（详见 `08`）。
